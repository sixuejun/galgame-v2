# galgame-v2 设计文档

## 概述

galgame-v2 是一个完全重新设计的酒馆 Galgame 前端界面，定位为可玩的视觉小说体验。

**核心目标：**

- 区块（block）用完自动切楼层，呈现连贯的剧情阅读体验选项
- 支持浏览所有历史楼层，每楼层内独立翻页
- 完整保留现有 galgame 的所有功能（弹幕、生图、立绘、背景等）
- 架构清晰，文档完善，方便后续维护

**与 galgame-v1 的核心区别：**


| 方面     | v1                                  | v2                                |
| -------- | ----------------------------------- | --------------------------------- |
| 渲染层   | `host: 'div'`，每个楼层一个组件实例 | `host: 'iframe'`，只渲染在第 0 层 |
| 数据获取 | 依赖脚本 push 楼层面板变量          | iframe 自主拉取所有楼层数据       |
| 楼层浏览 | 不支持                              | 支持历史楼层浏览                  |
| 块级翻页 | 当前楼层内                          | 当前楼层内 + 自动切楼层           |
| 代码结构 | 功能堆砌，耦合严重                  | 分层清晰，职责明确                |

## 模块总览

galgame-v2 按功能分为四大模块，各模块职责清晰、独立演进：

```
galgame-v2/
│
├── [1] VN舞台       — 视觉小说核心体验，所有与"显示和阅读"直接相关的部分
│
├── [2] 世界书联动   — 从世界书获取资源，世界书第二 API 提示词过滤
│
├── [3] 卡牌与生图   — 生图请求、结果管理、卡片队列，含第二 API 生图提示词生成
│
└── [4] 玩法        — 独立游戏模块，以插件（Plugin）形式挂载，可灵活扩展
    ├── [4A] 经济系统  — 商店（AI动态商品）、背包、工坊、资金日志
    ├── [4B] 事件系统  — 谜题（AI动态谜题）、末世通讯
    └── [4C] 娱乐系统  — 末世之路、2048
```

## 模块一：VN 舞台（核心）

VN 舞台是 galgame-v2 的核心模块，所有与"显示和阅读"直接相关的部分都在这里。

### 1.1 模块边界

**包含：** 对话框、背景、立绘、CG、弹幕、打字机、翻页导航、历史面板、自动播放、黑屏转场、主题/皮肤

```
│   ├── BlacktextOverlay.vue    # 黑屏文字转场（全屏遮罩）
│   ├── ChoicePanel.vue         # 选项面板（覆盖在对话框上）
```

### 1.4 交互流程

**三层导航结构回顾：**

```
dialogues[楼层索引].blocks[块索引]
                      ↑ 翻页只看块索引
                      ↑ 块越界才切楼层索引
```

**用户点击对话框 / 按 → 键：**

```
→ nextBlock()
    → 当前楼层内还有下一块？
        → 是：currentBlockIndex++，显示下一块
        → 否（已在最后块）：
            → 还有下一楼层？
                → 是：currentDialogueIndex++，currentBlockIndex=0，切换楼层
                → 否：停在最后块，等待新消息
    → 触发打字机效果
```

**按 ← 键：** 同理，块越界则切换到上一楼层的最后一块。

**流式输出过程中：**

```
watch context.message 收到新文本
  → 更新 dialogues[当前楼层].message（实时拼接）
  → 实时提取 <dm> 弹幕 → danmakuStore.pushDanmaku()
  → 实时提取 <background>/<cg> 标签 → 通知卡牌模块处理
```

**新消息完整到达时（CHARACTER_MESSAGE_RENDERED）：**

```
→ dialogues.push(新楼层)
→ currentDialogueIndex = dialogues.length - 1
→ currentBlockIndex = 0
→ 自动跳转到最新楼层
```

### 1.5 打字机效果与自动播放

**打字机效果：**

- **速度**：由 `settings.textSpeed` 控制（1-10），映射到毫秒延迟
- **跳过**：打字过程中点击对话框 → 直接显示完整文本
- **心理描写**：`*内容`* 格式解析为斜体灰色文字，与普通台词区分

**自动播放等待逻辑（串行模式）：**

```
动画播完 → 等待打字机一个字一个字打出来 → 再自动翻页
```

为了确保楼层间衔接流畅，系统会**提前预加载**上一个和下一个楼层的数据，使用户翻页时感觉流畅无阻。

### 1.6 黑屏转场设计

- **触发**：`currentBlock.type === 'blacktext'` 时显示全屏遮罩
- **动画**：遮罩淡入（500ms）→ 文字淡入（450ms，延迟 120ms）
- **交互**：左半屏点击 = `prevBlock()`，右半屏点击 = `nextBlock()`
- **按键**：← 键 = 退回，→ 键 = 前进

## 模块二：世界书联动

世界书联动模块负责从酒馆世界书获取游戏所需的图片资源（立绘、背景、CG），以及与游戏进度/数据相关的显示（角色状态、成就列表）。

### 2.1 模块边界

**包含：** 世界书资源加载、角色状态显示、成就列表、玩家头像上传

**不包含：** 生图请求（属于"卡牌与生图"）、对话框渲染（属于"VN 舞台"）、玩法逻辑（属于"玩法"）

### 2.2 组件清单

```
世界书联动/
├── components/
│   ├── CharacterPanel.vue       # 角色状态面板
│   │   ├── CharacterCard.vue    # 单个角色卡片
│   │   └── AvatarUpload.vue     # 头像上传组件
│   ├── AchievementNotch.vue     # 成就刘海入口
│   ├── AchievementList.vue      # 成就列表面板
│   └── WorldbookManagerPanel.vue # 世界书管理面板（可选）
│
├── store/
│   ├── characterStore.ts        # 角色数据（从世界书/MVU 读取）
│   └── achievementStore.ts      # 成就状态
│
└── utils/
    └── worldbookLoader.ts       # 世界书资源加载与匹配
```

### 2.3 各组件职责


| 组件                        | 职责                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------- |
| `CharacterPanel.vue`        | 显示所有角色列表（立绘、名称、数值）；点击角色展开详情；支持玩家头像上传（本地/链接） |
| `CharacterCard.vue`         | 单个角色卡片：头像 + 名称 + 好感度/等级/解锁状态                                      |
| `AvatarUpload.vue`          | 玩家头像上传；支持本地上传（Blob URL）和链接输入两种方式，预览和删除                  |
| `AchievementNotch.vue`      | 顶部成就入口（Notch 形式）；显示世界崩坏程度；展开时以 2 秒间隔轮询成就状态           |
| `AchievementList.vue`       | 成就列表；已解锁/未解锁/进行中分类显示；角色成就支持三态循环（线框→进行中→已完成）    |
| `worldbookLoader.ts`        | 加载世界书条目；根据角色名/场景名模糊匹配资源 URL                                     |
| `WorldbookManagerPanel.vue` | 世界书管理面板；可视化配置条目的目标 API、关联功能、自动控制；支持导出/导入 JSON      |


### 2.4 世界书资源匹配规则

立绘、背景、CG 的资源均从世界书加载，**采用按需加载策略**——用到时才加载，按角色名/场景名匹配后实时获取 URL。

**匹配规则：**

- **资源来源**：世界书条目中的 `textMappings` 字段
- **匹配方式**：规范化后模糊匹配（去除特殊符号、转小写）
- **缓存**：已加载的资源缓存到 Map，避免重复读取

**关于 MVU 变量框架**：角色好感度、数值等游戏数据可以通过 MVU 变量框架存储在世界书中（`_.get(message.data, 'stat_data')`）。V2.0 可以选择是否接入 MVU，如果接入，角色面板的数值从 MVU 读取。

### 2.5 角色状态数据来源

```
方案 A（不依赖 MVU）：
  → 角色数据存储在剧本提示词/世界书条目的固定格式中
  → worldbookLoader 解析并加载

方案 B（依赖 MVU）：
  → 角色数据通过 MVU 命令 [[setvar::角色.白娅.依存度=85]] 存储在楼层变量中
  → 从 message.data.stat_data 读取
  → AchievementStore 监听 VARIABLE_UPDATE_ENDED 事件
```

### 2.6 成就系统

> **说明**：成就系统保持与原版 galgame 完全一致，不做额外扩展。

#### 2.6.1 世界崩坏程度

`worldCollapseDegree`（0-100）代表世界的崩坏程度，影响当前阶段（Stage）判定，进而决定哪些成就可以显示。

```
worldCollapseDegree → Stage（阶段）→ 成就列表筛选
```

`worldCollapseDegree` 存储在酒馆变量中，成就要刘海组件（`AchievementNotch.vue`）从 `stat_data.世界崩坏程度` 读取并实时轮询更新。

#### 2.6.2 成就三态系统

普通成就只有两种状态：未完成 ↔ 已完成。

角色成就（带 `character` 字段）支持三态循环：


| 状态           | 触发条件 | 界面表现                     |
| -------------- | -------- | ---------------------------- |
| 线框（未开始） | 默认     | 灰显，线条轮廓               |
| 进行中         | 点击开始 | 高亮，填充色                 |
| 已完成         | 再次点击 | 完整高亮，可点击取消回到线框 |


#### 2.6.3 自动轮询机制

展开成就面板时，以 **2 秒间隔**轮询酒馆变量中的成就状态，支持热更新——无需关闭面板，奖励触发后成就状态会自动刷新。

### 2.7 足迹系统

足迹是一种可以穿插在正文中的收集型卡片，用于记录玩家在游戏中的重要时刻。参考贴纸卡片设计。

#### 2.7.1 消息格式

```
【足迹：（☀️）标题|触发条件：xxx|奖励：xxx|评价："xxx"】
```

**正则表达式：**

```regex
/\*{0,2}【\s*(?:触发)?成就[^：:|｜]*?[：:|｜]\s*[（(]?\s*([^\s)）|｜】]{1,3})\s*[)）]?\s*([^|｜】]*?)\s*[|｜]\s*(?:触发)?(?:条件)?[：:]?\s*([\s\S]*?)\s*[|｜]\s*(?:奖励)?[：:]?\s*([\s\S]*?)(?:\s*[|｜]\s*(?:系统)?(?:评价)?[：:]?\s*([\s\S]*?))?\s*】\*{0,2}/gu
```

**解析字段：**

| 字段 | 示例                | 说明           |
| ---- | ------------------- | -------------- |
| 图标 | ☀️                   | Emoji          |
| 标题 | 初次相遇            | 显示在贴纸上   |
| 条件 | 经营步入正轨        | 显示在标题上方 |
| 奖励 | 0小判               | 右下角显示     |
| 评价 | "主人已经不需要..." | 卡片内文字     |

#### 2.7.2 显示流程

```
消息解析
    ↓
检测到【足迹：...】格式
    ↓
在当前位置渲染遮罩层
    ↓
弹出贴纸卡片（带渐显动画）
    ↓
用户点击任意处
    ↓
卡片淡出 + 遮罩消失
    ↓
继续显示后续内容
```

#### 2.7.3 卡片样式要点

```
┌────────────────────────────────┐
│  ✦                          ✦  │  ← 装饰星星（浮动动画）
│                                │
│  ┌ 触发条件：初次相遇 ┐      │  ← 条件标签（贴在标题上方）
│  │                          │  │
│  │     ☀️ 初次相遇          │  │  ← 标题 + Emoji（描边效果）
│  │                          │  │
│  └──────────────────────────┘  │
│                                │
│  ┌────────────────────────┐  │
│  │   命运的相遇开始了...   │  │  ← 背景文字区（斜体）
│  └────────────────────────┘  │
│                     💰 +10    │  ← 奖励标签
└────────────────────────────────┘
```

**核心 CSS 变量：**

```css
:root {
  --c-brown: #402B1E;
  --c-brown-light: #523a2a;
  --c-cream: #F8F2E6;
  --c-stroke-inner: #000000;
  --c-stroke-outer: #E0D6C8;
  --c-accent: #FFD700;
  --c-tag-red: rgba(211, 84, 94, 0.9);
}
```

#### 2.7.4 字段截断规则

| 字段     | 最大长度 | 截断方式          |
| -------- | -------- | ----------------- |
| 标题     | 8 字符   | 尾部截断          |
| 条件     | 15 字符  | 尾部截断 + 省略号 |
| 背景文字 | 25 字符  | 尾部截断 + 省略号 |

| 系统 | 显示方式               | 用途         |

### 2.7 Live2D 立绘集成

Live2D 与静态立绘图片**互斥**，同一角色不会同时拥有两者。`spriteType` 由角色在世界书中的配置决定，**默认优先 Live2D**。

#### 2.6.1 渲染模式


| spriteType | 渲染方式                        | 说明                                 |
| ---------- | ------------------------------- | ------------------------------------ |
| `image`    | `<img>` 标签                    | 静态立绘图片，按 scale/position 定位 |
| `live2d`   | `<canvas>` + WebGL + Cubism SDK | Live2D 模型渲染，支持动作/表情/触摸  |
| `none`     | 无                              | 不显示任何角色立绘                   |


#### 2.6.2 实现参考

基于 `@Live2dRender`（Cubism Native SDK），参考 `参考/Live2dRender/` 项目：

- `src/main.ts` — 对外暴露 `initializeLive2D()`、`setExpression()`、`setMessageBox()` 等初始化和交互接口
- `src/lapplive2dmanager.ts` — 模型管理器，单例模式，`startMotion()` / `startRandomMotion()` 驱动动作，`onTap()` 处理触摸反馈
- `src/lappmodel.ts` — 模型实现，`hitTest()` 判断点击区域，`preLoadMotionGroup()` 预加载 motion，`setExpression()` 切换表情
- `src/lappdefine.ts` — 配置常量：待机分组 `MotionGroupIdle`、点击分组 `MotionGroupTapBody`、头部/身体区域名 `HitAreaNameHead/Body`

注意：`参考/live2d与galgame界面前端/` 中的 `pixi-live2d-display` 方案**不采用**，以 `@Live2dRender` 为准。

#### 2.6.3 关键词驱动动作与表情

Live2D 的 motion/expression 与静态立绘**共享角色名匹配流程**，匹配 key = `角色名 + 关键词`，与立绘的姿态关键词映射完全一致。

**匹配流程：**

```
[[character||角色名：程北极||台词：{{叹气}}]]
  → block.character = '程北极'
  → block.motion = '叹气'
  → 匹配 key = normalizeText('程北极叹气')
  → 在 ModelResource.motions[].textMappings 中匹配
  → 找到后返回 file URL
  → 传递给 LAppLive2DManager.startMotion(file)
```

**匹配规则**：`normalizeText(character + motion/expression)` = `normalizeText(textMappings 中的某个值)` 时匹配。

**简化说明**：

- 不需要 `motionType` 区分动作/表情，统一由 `textMappings` 匹配
- 不需要分组（group）概念
- 不需要 index，直接用文件 URL 驱动
- 找不到匹配时：motion 不播放，expression 不切换

#### 2.6.4 触摸互动系统

触摸互动是一种与角色互动的方式，适用于 Live2D 模型和静态立绘，**独立于动作/表情匹配流程之外**。与角色绑定，由 `touchAreas[]` 定义。

##### 2.6.4.1 区域配置

在世界书模型 JSON 的 `touchAreas[]` 中定义：

```json
{
  "touchAreas": [
    {
      "id": "head",
      "label": "头",
      "hitbox": { "x": 0.45, "y": 0.1, "width": 0.2, "height": 0.2 },
      "motionGroup": "程北极摸头动作",
      "longPressMotionGroup": "程北极长按摸头动作",
      "effectType": "heart",
      "shortPressThreshold": 400,
      "effectDuration": 1200
    },
    {
      "id": "cheek",
      "label": "脸颊",
      "hitbox": { "x": 0.3, "y": 0.28, "width": 0.12, "height": 0.14 },
      "motionGroup": "程北极摸脸动作",
      "effectType": "heart",
      "shortPressThreshold": 400,
      "effectDuration": 1200
    }
  ]
}
```


| 字段                   | 说明                                                         |
| ---------------------- | ------------------------------------------------------------ |
| `id`                   | 区域唯一标识                                                 |
| `label`                | 显示名称（用于调试工具）                                     |
| `hitbox`               | 相对坐标（0-1），以角色立绘/Live2D 画布宽高为基准            |
| `motionGroup`          | 短按触发时随机选一个 motion 播放                             |
| `longPressMotionGroup` | 长按触发时随机选一个 motion 播放（可选，不配置则无长按效果） |
| `effectType`           | 特效类型：`ripple`/`heart`/`magic-circle`/`none`             |
| `shortPressThreshold`  | 短按阈值（毫秒），0~`effectDuration` 之间，默认为 400ms      |
| `effectDuration`       | 特效完整动画时长（毫秒），默认为 1200ms                      |


**注意**：`motionGroup`/`longPressMotionGroup` 与 `textMappings` 完全无关——它们是 motion 文件路径的分组，用于触摸互动触发；`textMappings` 是关键词到 `motions[].file` 的映射，用于对话块驱动。

##### 2.6.4.2 区域显示（调试工具）

每个触摸区域可以在立绘/Live2D 上方渲染一个半透明方框，方便根据模型外观调整 `hitbox` 坐标：

```html
<!-- 每个区域的调试方框 -->
<div class="touch-area-debug-box" :style="hitboxStyle(area)" />
```

- 调试模式下默认显示，可通过设置面板一键隐藏
- 方框颜色、透明度可配置

##### 2.6.4.3 渐进式特效

特效是一个**连续递进的动画**，按得越久越丰富。特效跟随鼠标/手指坐标实时移动。

```
特效时间轴：
0%────短按阈值(0.4s)────100%(1.2s)
 │←──短按区域──→│←──长按区域──→│
 短按触发点         长按触发点
```

**以 `heart` 特效为例的递进效果：**


| 时间段      | 效果                                                          | 触发       |
| ----------- | ------------------------------------------------------------- | ---------- |
| 0 ~ 0.4s    | 单个爱心从小圆点展开上升                                      | —          |
| 0.4s 时     | **短按判定**：此时松手 = 短按，触发 `motionGroup`             | 短按触发点 |
| 0.4s ~ 1.2s | 爱心逐渐增多、变大、轨迹更复杂                                | —          |
| 1.2s 时     | **长按完成**：触发 `longPressMotionGroup`，特效播放完毕后停止 | 长按触发点 |
| 1.2s+       | 持续按住则循环播放完整特效                                    | —          |


**以 `ripple` → `magic-circle` 为例的图案递进：**


| 时间段      | 效果                           | 触发       |
| ----------- | ------------------------------ | ---------- |
| 0 ~ 0.4s    | 单层水波纹外扩                 | —          |
| 0.4s 时     | **短按判定**                   | 短按触发点 |
| 0.4s ~ 1.2s | 水波纹上逐渐叠加旋转的符文圆阵 | —          |
| 1.2s 时     | **长按完成**                   | 长按触发点 |


**CSS 实现思路**（以 ripple→magic-circle 为例）：

```css
/* 特效容器，跟随鼠标/手指坐标 */
.touch-effect {
  position: absolute;
  pointer-events: none;
  z-index: 9999;
  transform: translate(-50%, -50%);
}
/* 短按段：水波纹（0~0.4s） */
.touch-effect .ripple-layer {
  animation: ripple-expand 0.4s ease-out forwards;
}
/* 长按段：魔法阵叠加（0.4s~1.2s） */
.touch-effect .magic-circle-layer {
  opacity: 0;
  animation: magic-circle-appear 0.8s 0.4s ease-out forwards;
}
@keyframes ripple-expand {
  0%   { transform: scale(0);   opacity: 1; }
  100% { transform: scale(2);   opacity: 0; }
}
@keyframes magic-circle-appear {
  0%   { opacity: 0; transform: scale(0.5) rotate(0deg); }
  100% { opacity: 1; transform: scale(2) rotate(180deg); }
}
```

##### 2.6.4.4 区域追踪与计时规则

- **特效跟随**：按下后特效定位于当前鼠标/手指坐标，移动时跟随
- **区域计时**：按下时开始计时，允许在区域内自由移动，移动期间持续计时
- **离开终止**：手指/鼠标离开当前区域时，立即终止计时，视为**短按**，触发 `motionGroup`
- **区域判定**：使用当前坐标实时判断是否在 `hitbox` 内

##### 2.6.4.5 短按与长按区分

**核心逻辑**：用计时时长 + 区域在位状态来区分。

```
用户按下 → 进入区域 A
  → 开始计时
  → 特效跟随鼠标坐标
  ↓
  ← 鼠标/手指在哪？
      ├─ 移出区域 A：
      │   → 立即停止计时
      │   → 停止特效动画
      │   → 触发 motionGroup[A]（短按）
      │
      └─ 仍在区域 A 内：
          → 继续计时，特效跟随坐标
          ↓
          ← 松手？
              ├─ 按住时长 < 短按阈值 → 短按 → 触发 motionGroup[A]
              └─ 按住时长 >= 短按阈值 → 长按 → 触发 longPressMotionGroup[A]
```

##### 2.6.4.6 完整交互流程

```
用户按下立绘/Live2D 画布
  ↓
获取鼠标/手指坐标 → 映射到 [0,1] 相对区间
  ↓
遍历当前角色的 touchAreas
  ↓ 命中哪个区域的 hitbox？
  ├─ 未命中：不处理
  └─ 命中区域 A：
       → 记录按下时刻 + 区域 A
       → 特效定位到当前坐标，播放渐进式动画
       → 特效跟随坐标（随 mousemove/touchmove 更新位置）
       ↓
       ← 坐标离开区域 A？
           ├─ 是：停止计时，停止特效，触发 motionGroup[A]
           └─ 否（持续在区域内）：
               ← 松手？
                   ├─ 按住时长 < 短按阈值 → motionGroup[A]
                   └─ 按住时长 >= 短按阈值 → longPressMotionGroup[A]
```

#### 2.6.5 动作循环

- **待机循环**：`defaultAnimation.motion` 指定的动作循环播放（当没有其他 motion 播放时触发）
- **放置行为**：等同于待机循环，无时间限制
- **打断机制**：新动作播放时自动打断旧动作（`@Live2dRender` 内置 priority 机制）

| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| `ImageDeck.vue`          | 扇形展开的卡片队列；左侧悬停展开，显示最新 N 张背景/CG 卡片                                            |

### 3.4 生图流程

**架构决策：照搬原 galgame 的生图机制。**

生图流程直接复用原 galgame 的卡牌队列和生图机制，新增的第二 API 生图提示词生成作为补充。

```
解析消息中的 <background>/<cg> 标签
  ↓
判断图片类型：
  - [[character||...||CG场景：xxx||...]] → cg
  - [[character||...||场景：xxx||...]] → background
  ↓
生图优先级：cg > background（可通过设置调整）
  ↓
调用 imageGenBridge.requestImage(prompt)
  → 发送 generate-image-request 事件到酒馆
  → st-chatu8 插件接收请求，调用 SD/NovelAI/ComfyUI 生图
  → 插件返回 generate-image-response 事件
  → 获取图片 URL / base64
  ↓
将图片注入到 cardStore.cards[]
  → ImageDeck 自动显示新卡片
```

### 3.5 脚本与 iframe 的通信

**架构决策：使用 window 对象通信（与原 galgame 一致）**

脚本和 iframe 通过 `window.__galgame_v2` 共享对象通信，脚本写入数据，iframe 读取。

### 3.6 第二 API 生图提示词生成

生图提示词可以由第二 API 动态生成，替代完全依赖主 AI 回复中的 `<background>` / `<cg>` 标签。

#### 3.6.1 触发时机

当新消息完整到达（`CHARACTER_MESSAGE_RENDERED` 事件），且当前楼层消息中**尚未包含**生图标签时，触发第二 API 请求。

#### 3.6.2 上下文传递策略

与弹幕生成一致，**只发送最后一个楼层**。


| ordered_prompts 位置           | 内容                            | 来源                                      |
| ------------------------------ | ------------------------------- | ----------------------------------------- |
| `'world_info'`                 | 世界书中过滤后的第二 API 提示词 | worldbookLoader 过滤后注入（见 2.4）      |
| `'chat_history'`               | **仅最后一条** assistant 消息   | iframe 自主截取 `dialogues[last].message` |
| `{role:'system', content:...}` | 内置生图提示词 system prompt    | 代码内硬编码                              |


#### 3.6.3 内置 System Prompt 示例

```javascript
`[System] 暂停角色扮演，禁止输出正文、状态栏和任何其它格式，
仅严格按照以下格式输出。回复必须是一组生图标签，不做任何解释。
指令：
1. 必须使用简体中文输出
2. 根据以下剧情内容，生成 1 组背景生图提示词
3. 提示词应为英文，用逗号分隔，适合 Stable Diffusion 等图像生成模型
4. 风格与剧情氛围一致
5. 仅输出一行，格式如下

格式：<background>
title###场景描述###
image###英文提示词，中文括号注明细节###
</background>

剧情内容：
{{last_message_content}}
`
```

#### 3.6.4 结果写回

第二 API 返回后：

1. **解析**：提取 `<background>` / `<cg>` 标签块
2. **写回楼层**：通过 `setChatMessages` 写入当前楼层消息末尾
3. **渲染**：提取标签，`imageGenStore` 触发 `imageGenBridge` 发起生图请求

> **降级策略**：若第二 API 请求失败，不生成生图提示词，不影响主流程。渲染层始终只依赖楼层消息中的生图标签。

#### 3.6.5 与主 API 的优先级

```
消息完整到达
  ↓
检测消息中是否有 <background> / <cg> 标签？
  ├─ 有 → 使用主 AI 生成的标签，直接触发 imageGenBridge
  └─ 没有 → danmakuSource / imageTagSource 配置决定
              ├─ 'main' → 不请求第二 API，等待下一条消息
              ├─ 'second' → 调用第二 API 生成标签，写回后再触发生图
              └─ 'disabled' → 禁用
```

#### 3.6.6 设置项

在 `settingsStore` 中增加：

```typescript
{
  imageGenEnabled: boolean,        // 总开关
  backgroundGenEnabled: boolean,   // 背景生图开关
  cgGenEnabled: boolean,           // CG 生图开关
  imageTagSource: 'main' | 'second',
  // 'main':   依赖主 AI 回复中的 <background>/<cg> 标签
  // 'second': 第二 API 生成（消息无标签时触发）
  imageGenPriority: 'cg' | 'background', // 两者同时存在时的优先级
}
```

### 3.7 生图标签格式

```

</background>
```

## 模块四：玩法（Plugin 系统）

玩法模块是 V2.0 的扩展系统，以独立 Plugin 形式存在。每个 Plugin 是独立的游戏功能模块，可以访问 VN 舞台数据，但与 VN 舞台完全解耦。

### 4.1 设计理念

- **松耦合**：Plugin 通过定义好的接口访问 VN 舞台状态，不直接依赖 VN 舞台内部实现
- **独立演进**：每个 Plugin 有自己的组件、Store、类型定义
- **可热插拔**：Plugin 可以通过设置开关启用/禁用

### 4.6 商店插件 — AI 动态商品生成

商店插件是末日世界的商店系统，AI 生成商品列表供玩家购买。

#### 4.6.1 核心玩法流程

```
1. 打开商店
   → 调用第二 API 生成商品列表（前端本地存储）
   → 显示商品网格（图标、名称、价格、描述）
2. 搜索/浏览商品
   → 输入关键词可重新生成商品
3. 将商品加入购物车
   → 购物车数据存储在前端本地
4. 一键结算
   → 扣除金币（MVU 变量）
   → 商品移入收集物（MVU 变量）
   → 通知 AI"买了xxx"（通过 injectInput 写回酒馆输入框）
5. 自动刷新（可选）
   → 按设定间隔自动调用第二 API 生成新商品
   → 每次刷新扣除手续费
```

#### 4.6.2 MVU 数据结构

商店相关的 MVU 变量：

```yaml
金币: 100              # 支付用，结算时扣除
收集物: {}             # 购买后商品移入这里，键是物品ID
```

**不需要** `shop.items` 变量——商品列表仅在前端本地存储，不持久化到 MVU。

#### 4.6.3 商品列表存储（前端本地）

```typescript
interface ShopItem {
  id: string           // 唯一标识（时间戳）
  name: string         // 物品名
  icon: string         // 图标（emoji）
  description: string  // 描述
  price: number        // 价格
  category: string     // 分类
}

// 前端本地存储
const shopItems = ref<ShopItem[]>([]);
```

#### 4.6.4 商品生成上下文


| ordered_prompts              | 内容                                        |
| ---------------------------- | ------------------------------------------- |
| `'world_info'`               | 世界书中过滤后的第二 API 提示词（人格设定） |
| `'chat_history'`             | 最近 3~5 条聊天记录（参考剧情阶段）         |
| `{role:'user', content:...}` | 用户输入的搜索关键词                        |


#### 4.6.5 AI 生成商品格式

AI 生成商品后，前端解析并展示（不写入 MVU）：

```yaml
$update:
  # 第一个商品
  "gameData.shop.items.item_1":
    id: "item_1"
    name: "能量饮料"
    icon: "🥤"
    description: "恢复50点体力"
    price: 50
    category: "消耗品"
```

前端解析后存储到本地 `shopItems`，不写入 MVU。

#### 4.6.6 购买结算流程

```
用户点击「结算」按钮
        ↓
┌─────────────────────────────────────┐
│ 1. 检查金币是否足够                  │
│    金币 < 总价 → 提示「金币不足」     │
├─────────────────────────────────────┤
│ 2. 扣除金币（MVU）                  │
│    [[setvar::金币={{当前金币-总价}}]]│
├─────────────────────────────────────┤
│ 3. 商品移入收集物（MVU）             │
│    [[setvar::收集物.{{id}}={...}]]  │
├─────────────────────────────────────┤
│ 4. 通知 AI（末日世界格式）             │
│    injectInput("[购买物品]\n...")    │
├─────────────────────────────────────┤
│ 5. 清空购物车                       │
└─────────────────────────────────────┘
```

**具体实现：**

```typescript
import { injectInput, getVariables } from '@tavern-types';

async function handleCheckout() {
  const { cart, cartTotal } = shopStore;

  // 1. 检查金币
  const currentGold = getVariables({ type: 'message' })?.金币 ?? 0;
  if (currentGold < cartTotal) {
    toastr.warning('金币不足！');
    return;
  }

  // 2. 构造 MVU 命令
  const mvuCommands: string[] = [];
  mvuCommands.push(`[[setvar::金币=${currentGold - cartTotal}]]`);

  // 3. 商品移入收集物
  for (const item of cart) {
    const itemData = { name: item.name, icon: item.icon, quantity: item.cartQuantity };
    mvuCommands.push(`[[setvar::收集物.${item.id}=${JSON.stringify(itemData)}]]`);
  }

  // 4. 通知 AI 的文本
  const purchaseText = cart.map(item => `商品名：${item.name} x${item.cartQuantity}`).join('\n');

  // 5. 注入酒馆输入框
  injectInput(`[购买物品]\n${purchaseText}\n[结束]`);
  injectInput(mvuCommands.join('\n'));

  // 6. 清空购物车
  shopStore.clearCart();
  toastr.success('购买成功！');
}
```

**使用物品（通知 AI）：**


**删除物品（不通知 AI）：**

### 4.7 工坊插件 — 角色挂机生产

#### 4.7.1 核心玩法流程

```
1. 打开工坊
   → 显示已解锁角色列表
   → 每个角色有生产速度和产出效率属性
2. 选择角色挂机
   → 选择角色开始生产
   → 角色自动累积收益
3. 收取产出
   → 点击收取，将收益转换为金币
   → 可暂停/继续/停止生产
4. 升级角色
   → 提升角色的生产速度和产出效率
   → 消耗金币解锁新角色
```

#### 4.7.2 角色属性


| 属性              | 说明                           |
| ----------------- | ------------------------------ |
| `productionSpeed` | 生产速度，决定收益累积频率     |
| `productionYield` | 产出效率，每次结算的收益量     |
| `level`           | 等级，影响速度和效率的成长曲线 |


#### 4.7.3 收益计算

```
每次结算收益 = productionYield × 当前等级倍率
结算频率 = 每 N 秒一次（N 由 productionSpeed 决定）
```

### 4.8 谜题插件 — 情报交换

核心玩法是"情报交换"——玩家出谜题，AI 来猜。

#### 4.7.1 核心玩法流程

```
1. 开始游戏
   → 输入谜底（谜底本地保存，不发送）
2. 提供提示
   → 输入第一条提示发送给 AI
   → AI 根据谜底和提示不断猜测
3. 继续互动
   → 玩家继续提供提示，AI 继续猜测
4. 结算
   → AI 猜中 → 胜利，发放金币奖励（50 + 轮数 × 20）
   → 玩家放弃 → 不结算
   → 随时可以放弃当前谜题，重新开始
```

| `{role:'system', content:...}` | 内置 NPC 口吻 system prompt    |


#### 4.7.4 奖励机制

AI 猜中谜底后，根据轮数发放金币奖励：`50 + 轮数 × 20`。玩家也可以随时放弃。

### 4.10 废土行路

#### 4.10.1 核心玩法流程

```
1. 打开棋盘
   → 显示格子地图，玩家位于当前位置
   → 悬浮骰子（WastelandDice）始终可见
2. 掷骰移动
   → 点击骰子，播放掷骰动画
   → 根据骰子值移动相应步数
3. 触发事件
   → 走到事件格子时，读取预生成的事件
   → choice 模式：弹出选项框，玩家选择后调用主 API
   → direct 模式：直接调用主 API 生成剧情
4. 结算效果
   → 事件触发后应用 HP/Sanity 等效果
   → 更新玩家状态
5. 继续移动
   → 重复步骤 2~4，直到到达终点
```

#### 4.10.2 事件生成上下文

| ordered_prompts | 内容 |
| --- | --- |
| `'world_info'` | 世界书中过滤后的第二 API 提示词（人格设定 + 当前剧情背景） |
| `'chat_history'` | 最近 1~2 条聊天记录（确定当前剧情阶段） |
| `{role:'system', content:...}` | 内置地图事件 system prompt |


#### 4.10.3 内置 System Prompt 示例

```javascript
`[System] 你是末日废土风格的地图事件生成器。根据剧情上下文生成事件列表。
指令：
1. 必须使用简体中文输出
2. 事件应与末日废土剧情背景相关
3. 包含正面、负面、中性事件
4. 每行一个事件，用 | 分隔各字段
5. 生成 9~12 个事件

格式：
事件标题|倾向|事件描述|结果说明|HP变化|SAN变化

倾向说明：
- negative：负面/危险（损失，如危险区域、误触装置、埋伏、污染等）
- positive：正面/有利（收益，如补给、捷径、情报、成功逃脱等）
- neutral：中性/不确定（随机性，如遇见 NPC、异常现象、临时交易等）

要求：
- 事件标题少于 6 个字
- 事件描述少于 30 字
- 结果说明少于 60 字
- HP/SAN 变化为整数，可为正负或 0，留空表示无变化
`
```

#### 4.10.4 预生成机制

棋盘游戏支持在地图初始化时**批量预先生成**所有格子事件，而非逐个实时生成：

```
地图初始化
  → 遍历所有格子
  → 调用 callSecondApi('boardGameEvent', { contentText })
  → 缓存事件结果到 boardgameStore.events[]
  ↓
玩家走到某格子时
  → 直接读取缓存中的事件
  → 无需等待 API 响应
  ↓
若 API 失败 → 使用内置事件池兜底
```

#### 4.10.5 事件发送模式

事件触发后的行为由 `boardGameEventSendMode` 设置控制：


| 模式               | 行为                                               |
| ------------------ | -------------------------------------------------- |
| `'choice'`（默认） | 将事件选项添加到 VN 选项框，玩家选择后再调用主 API |
| `'direct'`         | 直接调用主 API 生成剧情，无需玩家选择              |


#### 4.10.6 废土骰子组件

`WastelandDice.vue` 是棋盘游戏的悬浮骰子组件：

- 悬浮在界面上方，支持拖拽定位
- 点击后播放掷骰动画（Canvas 绘制）
- 骰子值随机 1-6，显示在骰子中央
- 掷出后自动触发棋盘移动逻辑

### 4.11 Plugin 生命周期

```
界面挂载
  → PluginManager 扫描已注册的 Plugin
  → 根据 setting.enabledPlugins 过滤
  → 初始化各 Plugin 的 store

Plugin 打开
  → 显示 Plugin 的 overlayComponent
  → Plugin 接收当前 DialogueUnit / currentBlock
  → Plugin 执行自己的逻辑

Plugin 关闭
  → 根据 closeBehavior 决定行为
  → 释放 Plugin 独占的资源

楼层/块变化时
  → 调用所有 Plugin 的 onDialogueChange 回调
  → 各 Plugin 根据新内容触发相应逻辑（如触发成就、发放奖励）
```

### 第二 API 共享服务

所有模块共用统一的第二 API 调用层，定义在 `共享/utils/api/secondApiClient.ts`。

#### 接口定义

```typescript
interface SecondApiConfig {
  enabled: boolean;
  baseUrl: string;     // 例如 https://api.deepseek.com/v1
  apiKey: string;
  model: string;       // 例如 deepseek-chat
  temperature?: number;
  maxTokens?: number;
}

export async function callSecondApi(
  task: string,        // 任务类型：'danmaku' | 'imageTag' | 'shop' | 'riddle' | 'comms' | 'mapEvent'
  payload: {
    contentText?: string;
    keyword?: string;
    lastMessage?: string;
    chatHistory?: string;
  }
): Promise<string | string[]>
```

#### 请求封装

```typescript
async function callCustomApi(task, payload, config: SecondApiConfig): Promise<string> {
  const endpoint = config.baseUrl.replace(/\/+$/, '') + '/chat/completions';

  const headers: Record<string, string> = { 'Content-Type': 'application/json' };
  if (config.apiKey) headers['Authorization'] = `Bearer ${config.apiKey}`;

  // 各 task 对应的 system prompt 由 callSecondApi 内部根据 task 类型拼接
  const systemPrompt = buildSystemPromptForTask(task, payload);
  const worldbookPrompts = worldbookLoader.getSecondApiPrompts();

  const body = {
    model: config.model,
    messages: [
      { role: 'system', content: [...worldbookPrompts, systemPrompt].join('\n\n') },
      { role: 'user', content: payload.contentText || payload.keyword || payload.lastMessage || ' ' },
    ],
    temperature: config.temperature ?? 0.7,
  };

  const response = await fetch(endpoint, {
    method: 'POST',
    headers,
    body: JSON.stringify(body),
  });

  if (!response.ok) throw new Error(`API error: ${response.status}`);
  const data = await response.json();
  return data.choices[0].message.content;
}
```

#### 配置持久化

第二 API 配置存储在 `共享/store/apiConfigStore.ts`，同时写入 localStorage 和酒馆脚本变量（可选）：

```typescript
// 共享/store/apiConfigStore.ts
export const useApiConfigStore = defineStore('apiConfig', () => {
  const config = ref<SecondApiConfig>(loadConfig());

  function updateConfig(partial: Partial<SecondApiConfig>) {
    config.value = { ...config.value, ...partial };
    localStorage.setItem('galgame_v2_api', JSON.stringify(config.value));
  }

  watchEffect(() => {
    replaceVariables(klona(config.value), { type: 'script', script_id: getScriptId() });
  });

  return { config, updateConfig };
});
```

```
酒馆网页
```

**关键约束：**

- iframe 样式隔离，可以使用 tailwindcss
- 所有楼层数据由 iframe 自主通过 `getChatMessages` 拉取

### 1.2 数据获取策略

```
┌─ iframe 挂载时 ─────────────────────────────────────────┐
│ getChatMessages('0-' + getLastMessageId())               │
│ → 获取所有 assistant 楼层                                 │
│ → 构建 dialogues[]                                        │
│ → 解析所有楼层文本（可选：按需解析，见 1.3）               │
│ → 定位到最后一个楼层                                       │
└──────────────────────────────────────────────────────────┘

┌─ 流式更新（watch context.message）──────────────────────┐
│ context.message 变化时：                                  │
│   → 更新 dialogues[当前楼层].message                      │
│   → 实时提取 <dm> 弹幕并显示                             │
│   → 实时提取 <image> 生图标签并触发生图                  │
│   → 实时提取 <background> 背景并切换                     │
└──────────────────────────────────────────────────────────┘

┌─ 新消息到来（CHARACTER_MESSAGE_RENDERED）──────────────┐
│   → 将新楼层追加到 dialogues[]                          │
│   → 自动跳转到最新楼层                                    │
└──────────────────────────────────────────────────────────┘

┌─ 聊天切换（CHAT_CHANGED）────────────────────────────────┐
│   → 清空 dialogues[]                                     │
│   → 重新 getChatMessages 全量加载                         │
└──────────────────────────────────────────────────────────┘
```

### 1.3 解析时机

采用**一次性全量解析**：

- 界面挂载时立即解析所有楼层
- 每次 watch context.message 时实时更新当前楼层数据
- 优点：历史面板瞬间显示，用户体验流畅
- 风险：聊天记录过长（数千层）时初始化可能较慢
  - 缓解：消息解析本身是纯字符串处理，速度极快
  - 后续可考虑：解析结果缓存到楼层变量，避免重复解析

## 第二章：数据结构

### 2.0 数据层级总览

数据分为**三层**，从宏观到微观：

```
第一层：dialogues[]         楼层数组 —— 酒馆里的每一条 AI 回复 = 一个楼层
第二层：DialogueUnit        单个楼层 —— 一个楼层的所有元数据
第三层：MessageBlock[]      块数组   —— 一个楼层内部可以分段显示的单元
```

**一个直观例子：**

假设酒馆对话如下：

```
[楼层 0]  [[character||Alice||台词：早上好]]
[楼层 1]  [[narration||旁白：她走进教室]]
          [[character||Bob||台词：今天天气不错]]
          [[narration||旁白：窗外飘起了雪]]
[楼层 2]  [[choice||去图书馆||去食堂]]
```

对应的数据结构：

```
dialogues[0]  messageId=0, blocks=[block0]         ← 1 个块
dialogues[1]  messageId=1, blocks=[block0, block1, block2] ← 3 个块
dialogues[2]  messageId=2, blocks=[block0]         ← 1 个块（选择框）
```

翻页时，用户在楼层 1 内看完 block0 → block1 → block2 后，自动跳到楼层 2 的 block0。

### 2.1 dialogues[] — 第一层：所有楼层数据

```typescript
interface DialogueUnit {
  /** 物理楼层号，对应酒馆 message_id */
  messageId: number;
  /** 原始消息文本（AI 回复的完整字符串） */
  message: string;
  /** 解析后的块数组（按需解析，见 2.2） */
  blocks: MessageBlock[];
  /** 该楼层是否已解析（false 时 blocks=[]） */
  parsed: boolean;
  /** 该楼层的弹幕数组 */
  danmaku: DanmakuItem[];
  /** 该楼层的生图标签 */
  imageTags: ImageTagBlock[];
}
```

### 2.2 blocks[] — 第二层：楼层内块结构

块（block）是楼层内可独立显示的最小单元。以 `[[character||...]]`、`[[narration||...]]` 等标签为边界切分。一个楼层可能有 1 个块，也可能有 N 个块。

```typescript
interface MessageBlock {
  type: 'character' | 'narration' | 'blacktext' | 'choice';

  // character 类型：角色台词
  character?: string;      // 角色名
  scene?: string;          // 场景描述
  motion?: string;         // 动作（Live2D 关键词 或 静态立绘姿态关键词）
  expression?: string;     // 表情（Live2D 关键词）
  text?: string;           // 台词
  isCG?: boolean;          // 是否 CG 场景

  // character 类型：立绘渲染模式（解析后填充，由角色名匹配结果决定）
  spriteType?: 'image' | 'live2d' | 'none'; // 默认 image，无资源则 none
  // 注：spriteType 由 worldbookLoader 根据角色名匹配结果决定，无需额外字段

  // narration / blacktext 类型：旁白或转场
  message?: string;        // 叙述文本

  // choice 类型：选项
  options?: string[];      // 选项列表，如 ['去图书馆', '去食堂']

  // 世界书资源匹配结果（解析后填充）
  sceneImageUrl?: string;  // 背景图片 URL
  cgImageUrl?: string;     // CG 图片 URL
  spriteImageUrl?: string; // 静态立绘图片 URL
  live2dMotionFile?: string;  // Live2D 动作文件 URL
  live2dExpressionFile?: string; // Live2D 表情文件 URL
  live2dModelConfig?: Live2dModelResource; // Live2D 模型配置（spriteType=live2d 时填充）
}

interface Live2dModelResource {
  modelName: string;        // 角色名
  modelPath: string;        // .model3.json URL
  textures?: string[];       // 纹理贴图 URL 数组
  motions: Array<{
    name: string;            // 动作名（如 "叹气"）
    file: string;           // motion3.json URL
    textMappings: string[];  // 关键词数组，用于对话块驱动
  }>;
  defaultAnimation?: {
    expression?: string;     // textMappings 中的值，如 "程北极微笑"
    motion?: string;        // textMappings 中的值，如 "程北极待机"
    autoLoop?: boolean;
  };
  touchAreas?: Array<{
    id: string;             // 区域唯一标识
    label?: string;         // 显示名称
    hitbox: { x: number; y: number; width: number; height: number }; // 相对坐标 [0,1]
    progressThreshold: number; // 触发所需点击次数
    motionGroup: string;     // 动作组标识，触发时在该组内随机选一个 motion
    effectType?: 'ripple' | 'magic-circle' | 'heart' | 'none'; // 点击特效类型
  }>;
  touchEffectDefault?: 'ripple' | 'magic-circle' | 'heart' | 'none'; // 默认特效类型
}
```

| 类型        | 格式         | 显示方式 |
| ----------- | ------------ | -------- |
| `character` | `[[character |          |
| `narration` | `[[narration |          |
| `blacktext` | `[[blacktext |          |
| `choice`    | `[[choice    |          |


**切分规则：**

- 每个 `[[...]]` 标签 = 1 个独立 block
- 裸文本（不在任何标签内）作为 `narration` block
- **user 消息不进入 dialogues[]**。用户点击选项 → 文本作为 user 消息发送 → AI 在下一条消息中复述（`[[character||角色名：{{user}}||...]]`）→ 正常参与翻页

### 2.3 danmaku — 弹幕结构

```typescript
interface DanmakuItem {
  text: string;           // 弹幕文本

  fontSize?: 'small' | 'medium' | 'large';
```

**弹幕隔离规则：**

- 每个楼层的 `danmaku[]` 只在该楼层显示
- 切换楼层时清空上一楼层的弹幕
- 流式过程中实时提取并显示新弹幕

### 2.3 第二 API 弹幕生成

弹幕生成采用**消息完整后触发**模式，不在流式过程中请求。

#### 2.3.1 剧情文本变量

每条消息生成完毕后，自动将剧情文本写入酒馆聊天变量，供 AI 在生成时使用：

```typescript
// 在 GENERATION_ENDED / CHARACTER_MESSAGE_RENDERED 事件中
const plainText = extractPlainTextFromContent(rawMessage);
insertOrAssignVariables({ 剧情文本: plainText }, { type: 'chat' });

// AI 在生成时可以直接使用 {{getvar::剧情文本}}
```

**内容来源**：`剧情文本` 从消息的 `<content>` 标签内提取，不包含格式标签（`[[...]]`）和特殊标签（`<dm>`、`<background>` 等）。

#### 2.3.2 触发时机

当新消息完整到达（`CHARACTER_MESSAGE_RENDERED` 事件），且当前楼层消息中**尚未包含** `<dm>` 标签时，触发第二 API 请求。

#### 2.3.3 上下文传递策略

**只发送最后一个楼层（刚生成的楼层）**，而非全部聊天记录，以保证 AI 专注度。

请求上下文由三部分组成，通过 `ordered_prompts` 传递：


| ordered_prompts 位置 | 内容 | 来源 |
| --- | --- | --- |
| `'world_info'` | 世界书中过滤后的第二 API 提示词 | worldbookLoader 过滤后注入（见 2.4） |
| `'chat_history'` | **仅最后一条** assistant 消息 | iframe 自主截取 `dialogues[last].message` |
| `{role:'system', content:...}` | 内置弹幕生成 system prompt | 代码内硬编码 |


> **重要**：不使用 `'char_persona'`，因为弹幕是从玩家/读者视角发出的，不需要角色扮演。

#### 2.3.4 内置 System Prompt 示例

```javascript
`[System] 暂停角色扮演，禁止输出正文、状态栏和任何其它格式，
仅严格按照以下格式输出。回复必须是一段弹幕文本，不做任何解释。
指令：
1. 必须使用简体中文输出
2. 根据以下剧情内容，生成 3~5 条观众视角的弹幕
3. 每条弹幕不超过 15 个字，风格符合剧情氛围
4. 用 | 分隔每条弹幕，不要加其他符号
格式：弹幕1|弹幕2|弹幕3|弹幕4|弹幕5
`
```

剧情文本通过 `{{getvar::剧情文本}}` 在 system prompt 中注入（由 worldbook 过滤后的 ordered_prompts 传递）。

#### 2.3.5 结果写回

第二 API 返回后：

1. **解析**：按 `|` 分割，返回数组 `string[]`
2. **写回楼层**：拼接 `<dm>弹幕1|弹幕2|...</dm>`，通过 `setChatMessages` 写入当前楼层消息末尾
3. **渲染**：提取 `<dm>` 标签，更新 `DialogueUnit.danmaku[]`，由 `DanmakuLayer.vue` 按原有流程渲染

> **降级策略**：若第二 API 请求失败，弹幕不生成，不影响主流程。渲染层始终只依赖楼层消息中的 `<dm>` 标签。

#### 2.3.7 流式实时弹幕预览

弹幕支持在**流式输出过程中实时显示**，不需要等消息完整。

```typescript
// watch(context.message, (newMessage) => {
watch(context.message, (newMessage) => {
  // 实时提取 <dm>...</dm>

```

当弹幕和生图提示词生成都使用第二 API 时，可以合并为**一次 API 调用**（task = `'danmakuAndImageGen'`），节省请求次数和费用。

### 2.4 世界书第二 API 提示词过滤

参考原版 galgame 的实现，世界书条目通过"目标 API"属性来控制哪些条目发送给哪个 API。过滤逻辑在 `callSecondApi` 内部实现，不依赖世界书的 `type` 字段。

#### 2.4.1 条目增强字段

每个世界书条目在 `extra` 字段中扩展了三个属性：

```typescript
interface WorldbookEntryEnhanced {
  uid: number;
  name: string;
  enabled: boolean;
  content: string;
  extra?: {
    targetApi: 'main' | 'second' | 'both';  // 默认 'main'
    autoControl: boolean;                     // 默认 false
    linkedFeature?: 'danmaku' | 'imageGen'; // 关联的功能开关
  };
  _worldbookName: string; // 所属世界书名（非 extra 中的字段）
}
```

#### 2.4.2 targetApi 三种模式


| targetApi        | 发送给主 API | 发送给第二 API |
| ---------------- | ------------ | -------------- |
| `'main'`（默认） | ✅ 启用时发送 | ❌              |
| `'second'`       | ❌            | ✅ 启用时发送   |
| `'both'`         | ✅ 启用时发送 | ✅ 启用时发送   |


#### 2.4.3 过滤流程（核心实现）

在 `callSecondApi` 内部，调用第二 API 前会执行以下流程：

```
1. 遍历所有世界书（角色世界书 + 聊天世界书 + 全局世界书）
   → getEnhancedWorldbook() 读取条目及其 extra.targetApi

2. 调用 filterAndApplyWorldbookForSecondApi()
   → 找出所有 targetApi === 'main' 且 enabled === true 的条目
   → 临时将这些条目的 enabled 改为 false（记录原始状态）
   → 立即渲染世界书更新（render: 'immediate'）

3. 执行第二 API 请求
   → 此时酒馆系统只注入 targetApi 为 'second' 或 'both' 的条目

4. 调用 restoreWorldbookStates()
   → 将所有被临时禁用的条目恢复为原始 enabled 状态
   → 立即渲染恢复
```

关键代码逻辑：

```typescript
// 调用前：过滤
async function filterAndApplyWorldbookForSecondApi(): Promise<WorldbookEntryState[]> {
  const modifiedStates: WorldbookEntryState[] = [];
  const entries = await getEnhancedWorldbook();

  const needsUpdate = entries.filter(e => {
    const targetApi = e.extra?.targetApi ?? 'main';
    return targetApi === 'main' && e.enabled; // 只发给主 API 的条目，临时禁用
  });

  for (const entry of needsUpdate) {
    modifiedStates.push({ worldbookName: entry._worldbookName, uid: entry.uid, originalEnabled: true });
  }

  // 批量禁用
  await updateWorldbookWith(name, wb =>
    wb.map(e => {
      const targetApi = e.extra?.targetApi ?? 'main';
      if (targetApi === 'main' && e.enabled) return { ...e, enabled: false };
      return e;
    }),
    { render: 'immediate' }
  );

  return modifiedStates; // 返回记录用于后续恢复
}

// 调用后：恢复
await restoreWorldbookStates(modifiedStates);
```

#### 2.4.4 自动控制机制

当条目设置了 `autoControl: true` 和 `linkedFeature` 时，条目会根据对应功能开关自动启用/禁用：

## 第四章：翻页与导航

### 4.0 导航状态变量

导航涉及两个索引变量：


| 变量                   | 含义                                    |
| ---------------------- | --------------------------------------- |
| `currentDialogueIndex` | 当前在第几个楼层（dialogues 数组下标）  |
| `currentBlockIndex`    | 当前楼层内的第几个块（blocks 数组下标） |


显示时取的是：`dialogues[currentDialogueIndex].blocks[currentBlockIndex]`

### 4.1 块级翻页（当前楼层内）

```
用户点击对话框 / 按 → 键  →  nextBlock()
按 ← 键  →  prevBlock()

nextBlock():
  若 currentBlockIndex < 当前楼层blocks数-1：
      currentBlockIndex++      ← 正常前进一块
  否则（已在当前楼层最后块）：
      若 currentDialogueIndex < dialogues数-1：
          currentDialogueIndex++    ← 切换到下一楼层
          currentBlockIndex = 0      ← 从新楼层第0块开始
      否则：
          停在最后块，等待新消息       ← 流式状态

prevBlock():
  若 currentBlockIndex > 0：
      currentBlockIndex--      ← 正常后退一块
  否则（已在当前楼层第0块）：
      若 currentDialogueIndex > 0：
          currentDialogueIndex--    ← 切换到上一楼层
          currentBlockIndex = 上一楼层blocks数-1
      否则：
          阻止向左翻页（已是最早的楼层和块）
```

### 4.2 伪代码实现

**nextBlock()：**

```typescript
function nextBlock() {
  const blocks = dialogues[currentDialogueIndex.value].blocks;
  if (currentBlockIndex.value < blocks.length - 1) {
    // 当前楼层内还有下一块 → 直接前进
    currentBlockIndex.value++;
  } else if (currentDialogueIndex.value < dialogues.value.length - 1) {
    // 已到最后块，但还有下一楼层 → 跳转
    currentDialogueIndex.value++;
    currentBlockIndex.value = 0;
    // 预加载下一个楼层的相关资源（立绘、背景等）
    preloadAdjacentFloors();
  }
  // else: 已到最后楼层最后块 → 什么都不做，等新消息
}
```

**prevBlock()：**

```typescript
function prevBlock() {
  if (currentBlockIndex.value > 0) {
    // 当前楼层内还有上一块 → 直接后退
    currentBlockIndex.value--;
  } else if (currentDialogueIndex.value > 0) {
    // 已在第0块，但还有上一楼层 → 跳转
    currentDialogueIndex.value--;
    const prevBlocks = dialogues[currentDialogueIndex.value].blocks;
    currentBlockIndex.value = prevBlocks.length - 1;
    // 预加载上一个楼层的相关资源
    preloadAdjacentFloors();
  }
  // else: 已在最早楼层第0块 → 阻止
}
```

### 4.3 楼层数据预加载

为了确保自动播放时楼层间衔接流畅，系统会提前预加载相邻楼层的数据：

```
自动播放流程：
当前块 → 动画（转场等）→ 打字机逐字显示 → 等待 autoPlaySpeed 毫秒 → nextBlock()

预加载策略：
- 每次切换楼层时，同时预加载上一楼层的最后一块和下一楼层的块数据
- 预加载内容包括：消息解析结果、立绘/背景资源 URL
- 使用后台异步加载，不阻塞主流程
```

### 4.4 流式输出时的行为

```typescript
watch(context.message, (newMessage) => {
  if (!newMessage) return;

  if (当前没有正在显示的楼层) {
    // 首次收到消息 → 创建新楼层条目
    appendNewMessage(messageId);
    currentDialogueIndex = dialogues.length - 1;
    currentBlockIndex = 0;
  } else if (流式过程中) {
    // 正在生成 → 实时更新当前楼层的 message
    dialogues[currentDialogueIndex.value].message = newMessage;
    // 实时提取弹幕标签 → danmakuStore.pushDanmaku()
  }
});
```

当 `CHARACTER_MESSAGE_RENDERED` 事件触发时，意味着一条 AI 回复完整了，此时该楼层已完全生成，用户可以继续翻页。

### 4.5 选择框不阻止翻页

```
ChoiceBox.vue:
- 选项按钮区域：点击 → selectOption() → 发送消息
- 按钮以外的空白区域：点击事件穿透 → nextBlock()
```

实现方式：选项按钮不阻止事件冒泡，对话框底层的点击区域接收穿透事件。

### 5.1 mainStore — 核心状态

核心就是管理三个状态：**所有楼层数据**、**当前楼层索引**、**当前块索引**。显示时由 computed 组合它们。

```typescript

  // === 数据 ===
  /** dialogues[楼层索引] = 单个楼层的所有信息 */
  const dialogues = ref<DialogueUnit[]>([]);

  /** 当前在看第几个楼层（下标），范围 0 ~ dialogues.length-1 */
  const currentDialogueIndex = ref(0);

  /** 当前楼层内第几个块（下标），范围 0 ~ dialogues[currentDialogueIndex].blocks.length-1 */
  const currentBlockIndex = ref(0);

  /** 预览楼层索引（用于历史面板浏览，不影响主显示） */
  const previewDialogueIndex = ref(0);

  /** 是否正在流式输出 */
  const duringStreaming = ref(false);

  // === 计算属性 ===
  /** 当前楼层数据 */
  const currentDialogue = computed(
    () => dialogues.value[currentDialogueIndex.value]
  );

  /** 当前块数据（翻页导航的目标） */
  const currentBlock = computed(
    () => currentDialogue.value?.blocks[currentBlockIndex.value]
  );

  /** 是否已到最后楼层最后块（流式时等待新消息） */
  const isLastBlock = computed(() =>
    currentDialogueIndex.value === dialogues.value.length - 1 &&
    currentBlockIndex.value === currentDialogue.value?.blocks.length - 1
  );

  /** 是否已在最前楼层最前块 */
  const isFirstBlock = computed(() =>
    currentDialogueIndex.value === 0 &&
    currentBlockIndex.value === 0
  );

  // === 方法 ===
  function loadAllDialogues() { /* ... */ }
  function parseDialogue(index: number) { /* 按需解析指定楼层 */ }
  function nextBlock() { /* 见第四章 4.2 */ }
  function prevBlock() { /* 见第四章 4.2 */ }
  function appendNewMessage(messageId: number) { /* ... */ }

  return {
    dialogues,
    currentDialogueIndex,
    currentBlockIndex,
    previewDialogueIndex,
    duringStreaming,
    currentDialogue,
    currentBlock,
    isLastBlock,
    isFirstBlock,
```

### 7.3 错误处理与容错

本节描述各模块在异常情况下的 fallback 策略和错误展示规范，确保 v2 系统在边界情况下也能优雅降级。

#### 7.3.1 消息解析容错

**格式错误的标签**：解析器在遇到不完整的 `[[...]]` 标签时（如缺少闭合符 `]]`），使用保守策略：
- `matchBlock()` 在找不到匹配的 `]]` 时返回 `null`，外层循环跳过该位置并继续搜索，不会抛出异常
- 错误位置会被视为裸文本而非结构化块，裸文本在 `content` 标签外时直接忽略，在标签内时作为旁白处理
- `parseBlock()` 的 try-catch 包裹每个块的解析，单块失败不影响其他块

**流式过程中的不完整标签**：弹幕和生图标签在流式输出过程中可能只输出一半（如 `<dm>弹幕1|弹幕2` 尚未闭合）。处理策略：
- `extractDanmakuBlock()` 和 `extractImageTagBlocks()` 使用贪婪正则匹配，要求完整闭合标签才提取，半成品不产生任何输出
- 流式 watch 只在 `CHARACTER_MESSAGE_RENDERED` 触发时完整解析该楼层，此时消息已完全生成，不存在不完整标签
- 实时弹幕预览（非等待消息完整）在 `extractDanmakuBlock()` 返回空数组时静默跳过，不会触发错误状态

**世界书资源匹配失败**：当 `matchBackground()` / `matchSprite()` / `matchCG()` 找不到匹配时：
- 打印 `console.warn` 供调试，不抛出异常
- `MessageBlock` 中对应的 `sceneImageUrl` / `spriteImageUrl` / `cgImageUrl` 保持 `undefined`
- UI 层根据 `undefined` 渲染 fallback：
  - 立绘：背景渐变不变，不显示角色立绘
  - 背景：`BackgroundLayer.vue` 检测到 URL 为空时显示默认大气渐变背景
  - CG：`CgLayer` 检测到 URL 为空时不显示

#### 7.3.2 第二 API 请求容错

**超时和重试**：
- 超时阈值：`SECOND_API_TIMEOUT_MS = 30000`（30 秒）
- 重试次数：`SECOND_API_RETRY_COUNT = 2`（最多重试 2 次）
- 每次重试等待 `Math.pow(2, attempt) * 1000` 毫秒（指数退避）

**降级策略**：
- 请求失败后，记录 `secondApiConsecutiveFailures` 计数器
- 连续失败 3 次以上时，`secondApiStatus` 进入 `'degraded'` 状态，UI 显示警告指示器
- 弹幕生成失败 → 不显示弹幕，不影响主剧情流程
- 生图提示词生成失败 → 静默跳过，不触发生图
- 商店/谜题等玩法功能失败 → 弹出 toast 提示

**错误展示**：
- `ImageGenRetryPanel.vue` 显示生图失败的错误信息（图片 URL 加载失败 / 网络错误 / API 错误）
- 第二 API 调用失败时通过 toast 提示用户
- 错误日志通过 `console.error` 记录，便于调试

#### 7.3.3 聊天切换竞态

**场景**：用户在看历史楼层时，AI 生成了新消息（新楼层追加到 `dialogues[]`）。

**处理策略**：
- 追加新消息时，若用户当前不在最后一块（正在浏览历史），`wasAtLast` 判断为 `false`，**不自动跳转**到新楼层
- 只有当用户恰好在看最后一块时，才自动跟随到新楼层
- `wasAtLast` 通过比较 `currentBlockFlatIndex` 和 `flatLenBeforeParse - 1` 来判断

**流式过程中聊天切换**：流式 watch 和 `CHARACTER_MESSAGE_RENDERED` 回调同时触发时：
- 新消息追加由 `CHARACTER_MESSAGE_RENDERED` 事件驱动，与 watch 互不阻塞
- `appendNewMessage()` 内部有 `some(d => d.messageId === messageId)` 去重检查，避免重复追加
- `loadAllDialogues()` 在 `CHAT_CHANGED` 事件触发时先清空 `dialogues.value = []`，再重新加载

#### 7.3.4 用户消息游离状态

**数据路径**（已确认）：
- 玩家在 `DialogueInputPanel` 输入文本 → 直接 `createChatMessages()` 发送为 user 消息
- user 消息**完全不经过** `dialogues[]`，不参与楼层浏览
- AI 在下一条回复中以 `[[character||角色名：{{user}}||...]]` 格式复述玩家输入
- UI 识别 `角色名` 为 `<user>` 或 `user` 时，自动匹配玩家设定的头像/立绘（由 `showUserAvatarForCurrentBlock` 判断）

**角色名识别规则**：
```typescript
/^(<user>|user)$/i.test(block.character.trim());
```
- 匹配 `<user>` 或 `user`（不区分大小写），忽略前后空白
- 匹配成功后，按 `avatarDisplayMode` 决定渲染方式：
  - `'avatar'` → 显示玩家头像
  - `'sprite'` → 显示玩家立绘（若配置了立绘资源）
  - `'off'` → 不显示

### 8.2 架构设计原则

#### 8.2.1 单一职责原则

每个模块、组件、Store 只负责单一职责：

| 层级      | 职责                        | 禁止行为         |
| --------- | --------------------------- | ---------------- |
| Store     | 管理状态，提供读取/修改接口 | 直接操作 DOM     |
| Component | 渲染 UI，处理用户交互       | 包含复杂业务逻辑 |
| Utils     | 纯函数，数据处理            | 包含副作用       |
| API       | 与外部通信                  | 直接修改 Store   |

#### 8.2.2 依赖方向原则

```
┌─────────────────────────────────────────┐
│              UI 组件层                    │
│    (Vue 组件、模板渲染、用户交互)          │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│              Store 层                    │
│    (Pinia 状态管理、响应式数据)           │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│              工具层                       │
│    (API 调用、数据解析、工具函数)           │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│              类型层                       │
│    (接口定义、常量定义、Schema)           │
└─────────────────────────────────────────┘
```

**依赖方向：** 类型层 → 工具层 → Store 层 → UI 组件层

**禁止反向依赖：** UI 不能直接调用 API，Store 不能直接操作 DOM

#### 8.2.3 组合优于继承

避免使用继承构建复杂组件，优先使用组合：

```typescript
// ❌ 避免：继承
class BaseDialogueBox extends Vue {
  // ...
}
class ChoiceDialogueBox extends BaseDialogueBox {
  // ...
}

// ✅ 推荐：组合
const DialogueBox = defineComponent({
  components: {
    TypewriterText,
    DialogueNavButton,
    ChoiceBox,    // 可选组合
  }
});
```

#### 8.2.4 接口隔离原则

使用 TypeScript 接口定义组件和模块的契约：

```typescript
// 定义组件接口
interface IDialogueDisplay {
  readonly currentBlock: MessageBlock | null;
  readonly isTyping: boolean;
  readonly isFirstBlock: boolean;
  readonly isLastBlock: boolean;

  nextBlock(): void;
  prevBlock(): void;
  skipTypewriter(): void;
}

// 实现组件
const DialogueBox = defineComponent({
  implements: IDialogueDisplay,
  // ...
});
```

### 8.3 数据流设计

#### 8.3.1 单向数据流

```
┌──────────────────────────────────────────────────────────┐
│                      用户交互                            │
│                     (点击/输入)                           │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│                      组件事件                            │
│                emit('action', payload)                  │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│                      Store 动作                          │
│                  action() { /* 更新状态 */ }              │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│                      状态更新                            │
│              reactive state → computed                   │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│                      UI 更新                            │
│              computed properties → template              │
└──────────────────────────────────────────────────────────┘
```

#### 8.3.2 Store 通信规范

**Store 之间的通信必须通过以下方式：**

```typescript
// ✅ 推荐：在 Store A 中调用 Store B 的 action
// store/navigationStore.ts
export const useNavigationStore = defineStore('navigation', () => {
  const cardStore = useCardStore();  // 引入其他 Store

  function nextBlock() {
    // 更新导航状态
    currentBlockIndex.value++;

    // 触发其他 Store 的逻辑
    if (shouldLoadImage()) {
      cardStore.loadNextCard();
    }
  }
});

// ❌ 禁止：在 Store 中直接修改其他 Store 的 state
function badNextBlock() {
  const cardStore = useCardStore();
  cardStore.cards.value = [];  // 禁止直接修改
```

#### 8.5.3 Store 规范

```typescript
// ✅ 使用 setup store 语法
export const useNavigationStore = defineStore('navigation', () => {
  // === State ===
  const dialogues = ref<DialogueUnit[]>([]);
  const currentDialogueIndex = ref(0);
  const currentBlockIndex = ref(0);

  // === Getters ===
  const currentDialogue = computed(() => dialogues.value[currentDialogueIndex.value]);
  const currentBlock = computed(() => currentDialogue.value?.blocks[currentBlockIndex.value]);

  // === Actions ===
  function nextBlock() {
    if (currentBlockIndex.value < currentDialogue.value.blocks.length - 1) {
      currentBlockIndex.value++;
    } else if (currentDialogueIndex.value < dialogues.value.length - 1) {
      currentDialogueIndex.value++;
      currentBlockIndex.value = 0;
    }
  }

  // === 持久化 ===
  watchEffect(() => {
    saveStateToStorage({
      dialogues: dialogues.value,
      currentDialogueIndex: currentDialogueIndex.value,
    });
  });

  return {
    // State
    dialogues,
    currentDialogueIndex,
    currentBlockIndex,
    // Getters
    currentDialogue,
    currentBlock,
    // Actions
    nextBlock,
  };
});
```

#### 8.7.4 聊天记录过长风险评估

`getChatMessages('0-' + lastId)` 在聊天记录很长时需要关注以下量级：

| 楼层数      | 估算 DOM 文本量 | `allBlocksFlat` 长度 | 风险                                    |
| ----------- | --------------- | -------------------- | --------------------------------------- |
| < 100 层    | < 500 KB        | < 500 块             | **低**：无需优化                        |
| 100~500 层  | 500 KB ~ 2 MB   | 500~5000 块          | **中**：注意 `shallowRef`，避免深层响应 |
| 500~2000 层 | 2 MB ~ 8 MB     | 5000~20000 块        | **高**：需要虚拟滚动、按需解析          |
| > 2000 层   | > 8 MB          | > 20000 块           | **极高**：建议分页加载或存档分流        |

**已采用的防护措施**：
- `dialogues` 使用 `shallowRef`，避免每个楼层内每个字段都变成响应式代理
- 楼层采用**按需解析**策略（`parsed: boolean` 标记），初始只加载消息文本和基本元数据，`blocks`/`danmaku`/`imageTags` 在需要时才异步解析
- `parseCurrentFloor()` 有 try-catch 包裹，单楼层解析失败不影响其他楼层

**历史面板虚拟滚动**：`HistoryPanel` 中的楼层列表使用虚拟滚动，只渲染可视区域内的楼层卡片（参考 v1 的做法）。

#### 8.7.5 打字机效果与自动播放状态机

打字机和自动播放共同构成一个状态机，以下是各状态之间的转换规则（参考 galgame v1 实现）：

```
状态机变量：
- isTyping: boolean         // 打字机是否正在工作
- isAutoPlaying: boolean   // 自动播放是否已触发定时器
- autoPlaySpeed: number    // 设置值，映射到延迟 ms

状态转换：

[打字机效果]
- block 切换（watch currentBlock）→ 重置 charIndex=0, isTyping=true → 开始逐字显示
- charIndex >= fullText.length → isTyping=false，停止计时器
- 用户点击跳过（handleClickText）→ 立即清除计时器 → displayedText=fullText → isTyping=false

[自动播放]
watch([autoPlay, isTyping, hasChoices, isLastBlock])：
- autoPlay = false → 不触发
- autoPlay = true 且 isTyping = false 且 hasChoices = false 且 isLastBlock = false
  → 设置定时器：delay = max(500, 5000 - autoPlaySpeed * 400) ms → 到达后调用 nextBlock()
- 任一条件变化 → 清除当前定时器（onScopeDispose）

[choice 块特殊处理]
- hasChoices = true 时，自动播放定时器不启动（选项出现时暂停自动播放）
- 用户选择选项后 hasChoices=false，自动播放恢复

[黑屏转场 + 打字机]
- blacktext 块：遮罩淡入（500ms）→ 文字淡入（延迟 120ms）→ 再开始打字机
- 打字机完成后 isTyping=false，但不自动翻页（黑屏块需要用户点击左右区域翻页）

[自动播放中途被打断]
- 用户主动翻页 → navigateBlock 触发 → 当前 block 变化 → watch currentBlock 重置打字机
- 自动播放定时器被 onScopeDispose 清除，不干扰
```

## 附录：v1 经验总结

### 经验 1：Store 拆分要趁早

v1 的单 Store 导致后期维护困难。v2 应在初期就将 Store 按模块拆分，即使初期只有一个 Store，也应预留拆分结构。

### 经验 2：组件要足够小

v1 的 `DialogueBox` 承担了太多职责。v2 应遵循"一个组件做一件事"原则，组件越简单越容易测试和维护。

### 经验 3：CSS 变量要系统化

v1 的 CSS 变量命名不一致，后期改主题非常困难。v2 应建立完整的 CSS 变量系统，并使用 TypeScript 类型约束。

### 经验 4：类型定义要完整

v1 存在大量隐式 any 和类型缺失。v2 应从第一天就建立完整的类型系统，使用 strict 模式。

### 经验 5：文档要与代码同步

v1 的文档和代码经常脱节。v2 应建立文档同步机制，确保架构变更时文档同步更新。
