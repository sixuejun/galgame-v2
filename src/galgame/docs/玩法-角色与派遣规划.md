# 玩法：角色与派遣规划（草案）

本文档用于规划 `src/galgame` 内的「角色系统」与「派遣探索（废土行路）」玩法。

目标：把“生成内容 → 结构化解析 → 渲染 → 回写（变量/剧情）”这条链路落到可实现的数据结构与协议上，并明确每个模块各自负责什么。

> 备注
>
> - 本文是设计/规划文档，不是实现细节。具体实现可以后续拆成多个小任务。
> - 角色与派遣会与现有的消息格式规范（`消息格式规范.md`）并行：VN 主舞台仍然走 `<content>...</content>` 等硬协议；角色/商城/事件生成的结构化协议是**玩法内部协议**。

---

## 0. 术语与范围

- **角色（Role / Employee / Companion）**：玩家可管理的可派遣单位，有档案与状态，可装备技能标签。
- **技能标签（Skill Tag / Item Tag）**：可从商城获得的“可装备标签”，会影响派遣、工坊、通讯等玩法。
- **派遣（Dispatch / Expedition）**：把某角色派去某地点探索，期间产生事件/结算，最终产生记录。
- **记录（Run Log）**：一次探索的过程摘要、关键事件、收益、消耗等，建议保存到聊天变量。

本文覆盖：

1. 角色数据结构与面板能力
2. 技能标签的数据结构与获取（与商城对接）
3. 派遣探索的核心流程与事件生成协议
4. 变量存储策略（优先聊天变量）

---

## 1. 设计目标

### 1.1 玩家体验目标

- 有一个「角色管理面板」：像变量管理面板一样可视化编辑角色。
- 玩家能给角色装配从商城获得的技能标签。
- 玩家可以选择一个角色 + 一个地点进行派遣探索；探索过程产出事件与奖励，并形成可回看的记录。
- 角色能“参与”其他玩法：
  - 工坊：技能影响生产效率/产出
  - 通讯/猜谜：角色档案可作为人格 prompt，玩家直接“跟角色聊天”

### 1.2 工程目标

- **协议化**：LLM 输出必须是可解析的结构化文本（`<tag>...` + 行/字段分隔）。
- **可扩展**：角色与技能的字段允许后续增加；不强绑定具体 UI。
- **低耦合**：VN 消息协议（`消息格式规范.md`）与玩法协议分离。
- **抗漂移**：提供版本号、字段约束、容错解析策略。

## 2. 数据模型规划

建议把角色系统拆成三层：**档案（Profile）/ 装备（Loadout）/ 运行态（Runtime）**。

### 2.1 角色：档案（Profile，相对稳定）

用途：UI 展示、通讯人格、事件叙事风格。**生成角色时重点产出这一层数据**。

生成字段（尽量中文命名；可按需裁剪）：

- `id`：稳定标识（内部引用用 id，不用姓名）。**由系统按顺序自动生成**（例如 `char_001`、`char_002`）。
- `姓名`：2~12 字，不要求唯一（唯一性由 `id` 保证）。
- `外貌`：一句话外貌描述（建议 10~40 字）。
- `性格`：关键词列表或短句（建议用逗号分隔 3~6 个关键词，例如：冷静、嘴毒、可靠）。
- `出身`：出身/经历摘要（一句话）。
- `定位`：在队伍/组织中的定位（近侍/侦察/技师/医护/后勤/交涉…）。
- `说话风格`：口癖/语气/称呼习惯（用于“废土通讯/猜谜”的人格替换）。
- `标签`：数组（阵营、专长、危险倾向、社交倾向、价值观等）。

> 为什么要 `id`
>
> - LLM 生成/玩家编辑可能导致姓名变化；玩法引用必须稳定。
>
> 推荐：把“可用于 prompt 的短摘要”也当作档案字段（可选）
>
> - `简介`：一段 30~80 字的摘要（拼接到事件/通讯 prompt 时优先使用简介，避免上下文爆炸）。

### 2.1.1 角色：属性（Stats，数值底座 v1）

用途：提供一个“可计算”的角色差异底座，影响派遣/工坊等玩法的**概率与结算**，同时能反哺性格与叙事表现。

约定：所有属性评分为 **0~5 整数**（0=短板，3=平均，5=顶尖）。

字段（v1 固定 6 维）：

- `战力`
- `技巧`
- `智慧`
- `社交`
- `谨慎`
- `运气`

落地到现有玩法（以 `src/galgame/boardgame` 为参考实现）：

1. **派遣抽卡层（核心）**：在从事件池抽取事件时，按 `nodeType(trap/fortune/encounter)` 与 `tendency(negative/neutral/positive)` 做加权抽取。

- `谨慎`：降低 `negative` 权重（trap 格子加成更强）
- `运气`：提高 `positive` 权重（fortune 格子加成更强）
- `智慧`：在 encounter 格子上，把权重从极端结果推向 `neutral/positive`

> 备注：这一步只改变“从池里抽到哪张卡”的概率，不直接改 hp/sanity 数值；且不会破坏“用掉即删除”的事件池机制。

1. **派遣过程结算层**：事件效果落到 hp/sanity 时，`社交` 提供稳定增益。

- `社交`：
  - 提高 `Hp/Sanity`（恢复效率）

1. **派遣战斗扩展（可选，v1 先做设计）**：新增 `battle` 格子类型；在战斗结算中使用 `战力` 计算胜率，并将胜负映射为 hp/sanity 的变化。
2. **工坊收益（已存在可计算入口）**：工坊结算收益使用角色属性 `技巧` 作为乘数（与工坊等级加成叠乘），确保“换不同角色挂机”立刻有数值差异。

> 原则：属性提供“角色底盘”，技能标签（mods）提供“可构筑方向”，两者叠加但不要互相取代。

### 2.1.2 角色：特质（Traits，可选叙事层 v1）

用途：让角色在事件/通讯中表现出稳定人格差异。Traits 不强制参与数值结算，但可以作为：

- 事件文案风格与偏好（叙事）
- 运行态状态机触发阈值修正（可选，如更易加班/更易逃跑等）

### 2.2 角色：装备与技能（Loadout，可变）

用途：把“技能标签”装到角色身上，让角色在派遣/工坊/通讯等玩法中产生差异化表现。

建议字段：

- `已装备技能id列表[]`：装备的技能标签 id 列表（稳定引用用 id，不用技能名）。
- `技能（展开视图，便于面板编辑/展示）`：
  - 面板上可以把技能以“字典/列表”展示成：
    - `技能名称`：展示名
    - `效果描述`：一句话文案（来自商城效果描述）
    - `mods效果`：结构化效果（可选，但建议预留模板）

#### `mods效果` 模板（建议从一开始就预留）

即使早期先不做数值结算，也建议把 `mods效果` 设计成“可选字段”，以便后续逐步把纯文案变成可计算效果。

推荐把每条 mod 表示为三段：

- `域`：影响哪个玩法（派遣/工坊/猜谜…；通讯玩法一般用不上）
- `键`：具体效果键（速度/掉落/抗性/额外选项…）
- `值`：**除少数特殊效果键外，数值由系统自动随机生成**

示例（仅示意）：

- `派遣.掉落加成=+10%`
- `派遣.生命变化下限=0`（避免某类事件造成致命后果）
- `工坊.生产速度=+15%`

设计约定（与商城对接）：

- 我们把“效果键”做成白名单池（见下文的《技能 mod 白名单与数值范围（v1）》）。
- 商城生成技能类商品时：
  - LLM 可以自由生成技能名称与效果描述
  - 但 **Tag 必须包含一个 `mod:域.键`**，且 `域.键` 必须在白名单中
  - 系统会根据该 `域.键` 自动生成数值，并写入技能实例的 `mods效果`
  - 若不满足白名单/格式要求 → 不认可该技能（不展示/不可购买/不入库）

> 备注
>
> - 早期可以只存 `技能名称` + `效果描述`；`mods效果` 为空数组。
> - 一旦需要“结算可计算”，再逐步让商城生成/系统转换填充 `mods效果`。

### 2.3 角色：状态（Runtime，运行态/进度）

用途：派遣/工坊/冷却/疲劳，以及你提到的“逃跑/加班/休息”等状态机。

建议字段（尽量中文命名）：

- `状态`：枚举（建议统一为一套可扩展的状态值）：
  - `空闲`
  - `派遣中`
  - `工坊中`
  - `逃跑中`
  - `休息中`
  - `加班中`
  - `受伤`
- `当前任务`：派遣/工坊/

### 2.4 角色：记录（Logs，可追加）

用途：存一些“值得记录的小事”，包括但不限于：

- 废土行路：某次地图完成记录、关键事件、战利品
- 工坊：某段时间的工作记录、加班/摸鱼、事故
- 通讯：重要对话摘要、关系变化

建议字段：

- `记录[]`：数组，每条为结构体
  - `时间`：时间戳或可读日期
  - `类型`：派遣/工坊/通讯/其他
  - `标题`：短标题
  - `内容`：一段短文

> 编辑策略
>
> - 系统自动追加：派遣结算/工坊结算时自动写入。
> - 玩家手动编辑：面板中允许增删改（更像队伍日记/人物小传）。

### 2.5 技能标签（Skill Tag / Item）

技能标签来源：商城购买/剧情奖励。

最小字段：

- `id`：技能 id（建议入库时生成，不依赖商品名）
- `name`：技能名（通常来自商品名）
- `emoji`：展示用
- `desc`：文案描述（来自效果描述）
- `domains[]`：适用域（`dispatch` / `workshop` / `comms` / `riddle`）
- `mods[]`：可计算效果（例如 `dispatch_hp_bonus:+1`、`workshop_speed:+10%`）

> 说明
>
> - 早期可以先不做 `mods` 结构化，先用 `desc` 纯文案 + LLM 在事件生成时“读懂”技能；
> - 但只要开始做数值结算，就建议逐步引入 `mods`。

## 3. 变量存储策略（优先聊天变量）

你当前倾向“聊天变量应该就够了”。建议按以下分层存储：

- 聊天变量（`{type:'chat'}`）：
  - `roles`：角色字典（`角色id` → `档案/属性/特质/装备/状态/记录`）
  - `skillsInventory`：玩家拥有的技能标签库存（与商城购买对接）
  - `dispatchRuns`：派遣记录列表（或按地点/角色索引）
  - `dispatchActive`：当前未结算派遣（按 roleId 索引，用于“恢复现场”）
  - `settings`：玩法配置（开关、难度、显示选项等）

> `dispatchActive` 设计要点
>
> - 进入 `BoardGameModule` 时：先选 roleId。
> - 若存在 `dispatchActive[roleId]` 且状态为 `active`：直接恢复地图/事件池/当前 stats/log/seed，不重复生成。
> - 结算/中止时：将 active 写入 `dispatchRuns` 并清空 `dispatchActive[roleId]`。
> - 这样“角色系统最终存聊天变量”与“派遣不重复生成”两点能自然对齐。
> 角色记录建议
> - 每个角色下增加 `记录` 字段：一组可追加的条目。
> - 记录既可由系统自动写入（如“完成一次废土行路地图”），也允许玩家手动编辑（作为人物小传/队伍日记）。

- 脚本变量（`{type:'script'}`）：
  - 仅存 UI 偏好（面板折叠状态、最近筛选条件），避免污染存档叙事。

## 4. 结构化输出协议规划

### 4.1 商城商品列表协议（已定向采用）

你当前拟采用：

```text
<shop>
emoji|商品名|价格|效果描述|销量|Tag
...
</shop>
```

约束：

- 6~12 行
- 字段内部禁止出现 `|`
- `价格` 20~150 整数
- `效果描述` 20 字以内
- Tag 可空或短词（缺货/打折/畅销…）

用途映射：

- `emoji|商品名|效果描述` → 入库成技能标签/收集物（MVU 或聊天变量库存）
- `价格/销量/Tag` → 展示/购买交互

#### 技能类商品：`mod:` 机制（与商城对接的关键）

你希望把“技能”的可计算效果从 LLM 输出中剥离出来，改为：

- **LLM 只负责选中一个效果键（白名单中的 `域.键`）**
- **具体数值由系统随机生成并写入技能实例**

因此约定：**只有 Tag 中存在合法 `mod:` 的商品才被认可为“技能类商品”**。

技能类商品的 Tag 格式：

- 固定前缀：`mod:`（冒号中英文都可，建议实现时同时兼容 `mod:` 与 `mod：`）
- 机器字段：`mod:域.键`
- 例如：`mod:派遣.掉落加成`

Tag 分隔规则（当同时存在文案 tag 与 `mod:` 时）：

- 行协议仍然用竖线 `|` 分隔 6 列
- Tag 列内部：用英文逗号 `,` 分隔多个 tag
  - 示例：`畅销,打折,mod:派遣.掉落加成`

技能类商品建议的行格式（仍然保持 6 列不变）：

```text
emoji|商品名|价格|效果描述|销量|mod:域.键
```

规则：

- 每个技能商品**只能包含一个** `mod:`（单 mod）
- Tag 里允许再加其他文案 tag（如 `畅销`、`打折`），用逗号分隔即可
- 系统侧校验：
  - `域.键` 不在白名单 → **不认可**（不渲染/不可购买/不入库）
  - 存在多个 `mod:` → 不认可

购买规则建议（先写死，便于玩法平衡）：

- 技能类商品：每个技能实例限购 1
- 普通商品：按原逻辑

> 可选增强（不强制）
>
> - 在不改变 UI 展示的情况下，内部可为每条商品生成稳定 `id`（由代码生成哈希/自增），避免“同名不同物”冲突。

### 4.2 角色档案生成协议（建议新增）

为减少字段名漂移，建议使用 KV 行协议：

```text
<role_profile_v1>
id=char_xxx
name=...
appearance=...
personality=...
background=...
role=...
speech_style=...
tags=tag1,tag2,tag3
</role_profile_v1>
```

解析策略：

- 只读取标签内
- 允许缺字段（用默认值/空字符串）
- `id` 若缺失由代码生成

## 4.4 技能 mod 白名单与数值范围（v1）

本节定义“技能类商品/技能标签”可用的 `mod:域.键` 白名单，以及系统为每个键生成数值的建议范围。

### 4.4.1 约定

- `域`：`派遣` / `工坊` / `猜谜`
- `键`：从白名单中选择
- `值`：由系统生成
  - 大多数键：随机落在范围内
  - 少数键：固定值或枚举（例如布尔开关）

> 重要
>
> - 商城生成的技能商品只需要给出 `mod:域.键`；不需要给出具体数值。
> - 系统校验 `域.键` 在白名单内才认可该技能。

### 4.4.2 派遣（探索/结算向，适配废土行路 boardgame）

派遣技能需要贴合 `boardgame` 的实际玩法逻辑：

- 地图格子类型（nodeType）是“场景标签”，建议与“好/坏/中”强绑定：
  - `fortune`：好格子
  - `trap`：坏格子
  - `encounter`：中性格子
- 事件卡结果倾向（tendency）是“抽到这张卡后大概率发生什么”：`negative / neutral / positive`
- 事件池是“每张地图开局一次性生成 9~12 张卡，触发时从池中抽取并删除”
- 事件最终落地到：`hp` / `sanity` / `transfer`（传送）与一段 `message`
- 本玩法的金币/纪念品不按每个事件即时掉落，而是“到终点或强制结算时”统一结算生成

因此派遣技能建议分为三层（落点不同，不要混在一起）：

1. **抽卡层技能（核心）**：进入某类格子时，影响“抽到不同 tendency 的概率”或“抽卡机制”（多抽/重抽/增加选择）
2. **过程结算层技能（补充）**：当 `hp/sanity/transfer` 发生时，影响结算幅度或触发保底
3. **终点结算层技能（旅行青蛙式）**：影响最终结算金币/纪念品/小故事（由结算 prompt 生成，但要有硬约束与白名单键）

> 区分原则
>
> - **不建议**让技能直接修改地图生成（例如“让好格子变多/坏格子变少”）。地图建议主要由 seed 决定，技能主要影响“同样的格子里更可能抽到什么结果”。

#### A. 抽卡层技能（影响 tendency 概率 / 抽卡机制）

这类键只作用于“抽卡”，不直接改 hp/sanity 数值。

- `派遣.trap负面率降低`：+5% ~ +25%（进入 `trap` 格时，降低抽到 `negative` 的概率，转移到 `neutral/positive`）
- `派遣.fortune正面率提高`：+5% ~ +25%（进入 `fortune` 格时，提高抽到 `positive` 的概率）
- `派遣.encounter趋向中性`：+5% ~ +25%（进入 `encounter` 格时，提高抽到 `neutral` 的概率，降低极端结果）
- `派遣.多抽一张卡`：固定 `true`（进入格子时额外抽 1 张候选卡；选取规则由系统定义：例如“取更好 tendency”或“让玩家二选一”）
- `派遣.重抽一次`：5% ~ 25%（当抽到 `negative` 时，有概率重抽 1 次）
- `派遣.避开极端负面`：5% ~ 20%（当抽到的卡 `hp/sanity` 负值过大时，有概率重抽或替换为 `neutral`）

> 说明
>
> - 抽卡层的实现建议由系统完成（加权抽取/二选一/重抽），不依赖 LLM。

#### B. 过程结算层技能（影响 hp/sanity/transfer 幅度）

- `派遣.hp损失减免`：5% ~ 20%（当事件 hp 为负时按比例减免）
- `派遣.sanity损失减免`：5% ~ 20%（当事件 sanity 为负时按比例减免）
- `派遣.hp回复加成`：+10% ~ +30%（当事件 hp 为正时按比例增加）
- `派遣.sanity回复加成`：+10% ~ +30%（当事件 sanity 为正时按比例增加）
- `派遣.安全撤离保底`：固定 `true`（当 hp 或 sanity 归零触发强制结算时，结果至少为“撤离”而非“失败”；具体规则由系统定义）

#### C. 终点结算层技能（旅行青蛙式终点结算）

这类键不会改变旅途中每张卡的即时掉落，而是影响终点/强制结算时的：

- 金币（gold）总额
- 纪念品（souvenirs）数量/稀有度/品质
- `派遣.金币加成`：+5% ~ +25%（结算金币总额乘区间系数）
- `派遣.纪念品数量+1`：+1（固定）
- `派遣.纪念品稀有度提升`：+5% ~ +20%（提高稀有纪念品池的抽取权重）
- `派遣.空手而归保护`：固定 `true`（保证至少获得 1 件纪念品或少量金币；具体规则由系统定义）

> 说明
>
> - 结算收益由 AI 一次性生成时，建议在结算 prompt 中显式写：如何把这些 mod 的“值”转成金币/纪念品的约束。
> - 若你后续希望更强可控，建议让系统先算“金币/抽取次数”，AI 只负责把纪念品命名与写小故事。

#### D. （可选扩展）新增 `battle` 战斗格子与通用角色属性（v1 设想）

你可以考虑新增 `battle` 格子类型，让“战斗事件”由系统生成而非 AI 事件池生成：

- `battle` 格触发时：从系统内置的“怪物/战斗模板池”抽取一个战斗事件
- 结算时使用角色属性（例如 `战力/智慧/谨慎/运气` 等）计算胜率与结果：
  - 胜负会影响 `hp/sanity`
  - 可选：一定概率产生战利品（写入行路记录 `gameLog`，并在终点结算时影响金币/纪念品）
- 角色属性作为通用底座，未来可复用到工坊/猜谜/通讯等玩法

> 说明
>
> - 战斗格子的事件也可以复用同一个事件结构（title/description/tendency/effect），从而不改 UI。
> - 该扩展不影响当前版本的派遣抽卡体系，可作为 v2 后续加入。

## 5. 派遣玩法流程（高层）

### 5.1 一次派遣的输入

> 重要：派遣（废土行路）以“选择出行角色”为起点。
>
> - 每次进入 `BoardGameModule` 前先选择一个角色（roleId）。
> - 若该角色上次的派遣未结算（存在 active run），则直接恢复现场（地图/事件池/当前 stats/log/seed 等），避免反复生成。

输入字段：

- `roleId`：选择的角色
- `location`：地点名/地点标签
- `context`：当前剧情上下文
- `roleProfile`：该角色档案
- `roleStats`：该角色属性（0~5 六维：战力/技巧/智慧/社交/谨慎/运气）
- `equippedSkills`：装备的技能标签列表

### 5.2 生成 → 解析 → 渲染 → 结算

- 生成：LLM 根据地点 + 角色 + 技能生成事件池（9~12 条）
- 解析：解析 `<event>` 行，得到事件对象数组
- 渲染：在玩法 UI 里以卡片/列表展示“抽到的事件”或“当前事件”
- 回写（过程中）：
  - 途中 `hp / sanity` 建议**共用 BoardGame 的 stats**（不直接等同于角色面板的长期状态）
  - 但会在“最终结算”阶段把结果映射回角色的状态（例如：受伤/休息）
- 结算（到终点或强制结算触发时）：
  - 根据 `角色信息 + 行路记录 gameLog + 本次 hp/sanity 变化` 生成结算内容
  - 金币与纪念品（收集物）**不在每个事件即时给出**，而是在最终结算时由 AI 一次性生成（更像“旅行青蛙”的回家结算）
  - 部分技能可以影响收益（金币/纪念品数量、品质、稀有度等），但数值分配由系统控制或由结算 prompt 明确约束

#### 强制结算条件

- 到达终点：正常结算
- 途中 `hp` 或 `sanity` 归零：触发强制结算（可以表现为“受伤撤离 / 精神崩溃被迫返程”）

> 说明
>
> - “共用 hp/sanity”指的是：派遣过程中只维护一套短期 `stats`；角色的长期状态只在结算阶段更新。
> - 这样可以减少变量耦合，同时保留“派遣失败/疲劳/受伤”对角色的长期影响。

### 5.3 记录与结算（Run Log / 旅途小故事）

一次地图/地点探索结束后，建议生成两类可保存内容：

- **结构化结算结果（用于存档与数值）**
  - `runId` / 时间戳
  - `roleId` / `roleName`
  - `location`
  - `result`：成功/撤离/失败（强制结算）
  - `hpEnd` / `sanityEnd`
  - `reward`：
    - `gold`：金币变化（整数）
    - `souvenirs[]`：纪念品/收集物列表（字符串数组，允许重复）
- **旅途小故事（用于沉浸与回看）**
  - `story`：一段 200~600 字的小故事，由 AI 根据 `角色信息 + gameLog + 结算结果` 生成

结算生成方式：

- 由 AI 生成 `<settlement>` 协议（金币/纪念品/结果/故事），系统解析并校验

## 7. 风险与约束（提前写清）

- **上下文爆炸**：角色多、技能多时 prompt 会过长。
  - 解决：只拼当前角色 + 装备技能的摘要。
- **协议漂移**：LLM 偶尔输出多余文本或字段内出现 `|`。
  - 解决：使用 `<tag>` 截取 + 强约束 + 容错解析。
- **稳定引用**：用 `商品名/角色名` 作为 key 会漂移。
  - 解决：内部引入 `id`（即使 UI 不展示）。
- **叙事协议与玩法协议混淆**：VN 主舞台硬协议不能被玩法输出污染。
  - 解决：玩法生成走独立 API/独立消息或仅在玩法 UI 内消费，不直接当 VN 主舞台内容。
