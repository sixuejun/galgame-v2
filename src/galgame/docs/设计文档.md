# galgame（v1）设计文档

本文档描述 `src/galgame`（v1，可运行版本）的目标架构与重构边界。

本项目不创建一个并行的“真正 v2 工程目录”，而是：
- 以 v1 现有可运行实现为底盘
- 以“v2 需求”作为 **约束与验收标准**
- 在不破坏运行的前提下，对 v1 进行结构化重构

相关规范：
- 消息协议（强约束）：[消息格式规范](./消息格式规范.md)
- 第二 API Prompt（权威来源）：[SystemPrompt模板](./SystemPrompt模板.md)
- UI 蓝图与组件映射：[UI规划文档](./UI规划文档.md)
- 开发与分段推进：[开发指南](./开发指南.md)

---

## 1. 核心目标（v1 重构版）

1. **单实例渲染**：仅在第 0 楼渲染一个 UI 实例（iframe），避免“每楼层一个实例”的资源与状态问题。
2. **连续阅读体验**：以 block 为翻页单位，block 用尽自动跨楼层切换，阅读体验连贯。
3. **历史楼层浏览**：支持浏览任意历史楼层，并在每楼层内独立翻页。
4. **严格消息协议**：assistant 消息必须遵守 `<content> + [[...]] block` 协议；解析器以该协议为唯一输入。
5. **第二 API 统一层**：弹幕、生图标签、商店、谜题、系统聊天、桌游事件等任务统一调用；Prompt 由文档集中管理。
6. **主题系统统一**：通过 `--theme-*` 变量实现主题/皮肤/用户自定义 CSS 的可组合覆盖。
7. **玩法插件化边界**：Shop/Inventory/BoardGame/2048/Riddle/Comms 等玩法模块具备清晰输入输出，不侵入 VN 核心导航。

---

## 2. 非目标与约束

### 2.1 不做的事（非目标）

- 不新建 `src/galgame-v2` 作为并行实现
- 不要求一次性拆分 `src/galgame/store.ts` 为多个 store 文件
- 不要求一次性重写所有玩法模块

### 2.2 关键约束（必须遵守）

- **Store 外观保持单文件**（monolith facade）：对外维持 `useVNStore()` 与现有 action API，内部可逐步抽离。
- **消息协议强约束**：不提供旧格式兼容模式；不符合协议的消息视为无 VN 内容。

## 3. 运行形态（单实例 + 流式）

### 3.1 单实例渲染

v1 采用单实例 iframe 挂载，并只渲染在 `message_id === 0`。

价值：
- UI 状态（历史导航、主题、玩法进度等）不随楼层变化而丢失
- 可从 iframe 内主动拉取历史消息并维护统一的 dialogues 状态

### 3.2 流式更新

流式的本质是：同一个楼层的文本在生成过程中持续追加。

设计原则：
- VN 核心状态机需要区分：
  - `duringStreaming`（生成中）
  - `newMessageFinalized`（生成完成，楼层定稿）
- 弹幕/生图标签可在流式过程中提取，但“落盘/触发任务”要有去重策略。

## 4. 核心数据模型（v1 约定）

### 4.1 DialogueUnit（楼层单元）

v1 在 store 中维护 `dialogues: DialogueUnit[]`，每个元素代表一个物理楼层（message）。

建议字段语义：
- `messageId`: 物理楼层号（mes_id）
- `role`: assistant/user/system
- `message`: 原始文本
- `blocks`: 解析后的 block 列表（来自 `<content>`）
- `danmaku`: `<dm>` 提取结果
- `imageTags`: `<background>/<cg>` 提取结果
- `parsed`: 解析缓存标记

### 4.2 MessageBlock（block 单元）

block 是 VN 导航与渲染的最小单位，来自 `[[...]]` 协议。

至少包含：
- `type`: character/narration/choice/blacktext/user 等
- `message/text`: 展示文本
- 可选：scene、character、motion、expression、cgScene 等

---

## 5. 导航状态机（连续阅读的核心）

### 5.1 三层结构

- `dialogues[dialogueIndex]`：楼层序列
- `blocks[blockIndex]`：楼层内 block

### 5.2 翻页规则（规范）

- `nextBlock()`：
  - 若当前楼层存在下一 block，则 `blockIndex++`
  - 否则：
    - 若存在下一楼层，则 `dialogueIndex++` 且 `blockIndex=0`
    - 否则停留，等待新楼层

- `prevBlock()`：
  - 若当前楼层存在上一 block，则 `blockIndex--`
  - 否则：
    - 若存在上一楼层，则 `dialogueIndex--` 且 `blockIndex=last`

### 5.3 历史浏览与“跳转”

需要支持：
- 跳转到任意楼层
- 在目标楼层内按 block 翻页
- 回到最新楼层

玩法模块不得直接修改上述索引，只能通过 store 暴露的导航 action。

---

## 6. 第二 API：任务层与 Prompt（文档驱动）

### 6.1 任务层职责

- 接收任务 key + 上下文（剧情纯文本、结构化上下文、历史对话等）
- 选择 Prompt（来自文档）
- 发起请求并解析响应
- 把结果交给上层（例如：写回 `<dm>`、触发生图、刷新商店商品等）

### 6.2 Prompt 权威来源

本项目采用“B 方案”：Prompt 权威来源是 `src/galgame/docs/SystemPrompt模板.md`。

约束：
- Prompt 内容不可散落在代码、预设文件或 UI 文案中
- 若必须使用预设/EJS，应将其视为“运行时拼装机制”，但 Prompt 文本仍由文档提供

---

## 7. 主题系统：变量语义与覆盖优先级

原则：
- `--theme-*` 为稳定公共语义层
- Theme 包提供一组默认值（可按主题 id 切换）
- 用户自定义 CSS 可以覆盖 `--theme-*`（局部或全部）

目标：
- UI 组件不依赖具体主题实现（例如不硬编码某主题的颜色变量名）

---

## 8. 玩法模块：插件化边界（在 v1 内实现）

把玩法模块定义为插件（不一定立刻改目录/工程形态），但必须满足：

- 输入：
  - 只读当前 store 状态
  - 可选读取“当前剧情上下文”（必须经过标准提取函数）

- 输出：
  - 只能通过 store action 改变：金币、背包、交易日志、桌游状态等

禁止：
- 直接操纵 VN 导航索引
- 直接写 DOM/绕过消息协议把文本塞进 UI

---

## 9. 分段重构路线（文档层）

建议的验收顺序：

1. **协议与解析固定**：把消息格式规范当成硬接口
2. **导航状态机固定**：历史浏览 + 跨楼层连续阅读
3. **Prompt 文档权威化**：第二 API 所有 Prompt 迁移进文档并由代码引用
4. **主题语义层稳定**：统一 `--theme-*` 的含义
5. **玩法插件边界落地**：每个模块只通过 store action 与核心交互
