## 0. 模块依赖关系总览

```
┌──────────────────────────────────────────────────────────────┐
│                     角色系统（核心依赖层）                      │
│  types/role.ts → 扫描引擎 → CMD 协议 → ID 管理 → 格式化       │
└────────────────────────────┬─────────────────────────────────┘
                             │
        ┌────────────────────┴────────────────────┐
        ▼                                         ▼
┌─────────────────────────┐            ┌─────────────────────────┐
│    废土行路（boardgame） │            │        工坊 v2          │
│    依赖：角色数据+技能   │            │    依赖：角色状态+技能   │
│    依赖：技能 mod 白名单  │            │    依赖：技能 mod 白名单  │
│    依赖：角色记录写入    │            │    依赖：订单生成 prompt  │
└─────────────────────────┘            └─────────────────────────┘
```

**关键依赖链**：

1. 角色系统（阶段一）是所有玩法的基础，所有后续阶段均依赖阶段一的类型定义与扫描引擎。
2. 技能 mod 白名单（`docs/技能mod白名单.md`）是角色装备层和商城技能分页的校验依据，独立于角色系统先行确认即可。
3. 废土行路与工坊 v2 互不依赖，可并行开发，但共享角色系统的类型定义。
4. 角色记录写入（`docs/角色记录写入格式设计.md`）在废土行路和工坊 v2 的结算阶段调用，属收尾工作。

## 2. 阶段 0：基础设施确认

> 目标：在正式编码前确认所有跨模块的设计决策，避免阶段一之后频繁返工。

### 0.1 技能 mod 白名单定稿

**输入**：`docs/技能mod白名单.md`

**检查项**：

- [ ] **派遣域**（A~E）：所有键的「值类型/值范围/说明」与 `废土行路模块详细设计.md` 附录 A 一致，无冲突
  - 特别核对：派遣 A 抽卡层 `encounter趋向中性` 的上限在归一化后会失效（见原文档 §C.3）
  - 特别核对：险胜精神惩罚（§C.1）和再战阈值（§C.2）是否需要修正
- [ ] **工坊域**：通用键 + 冶炼/制药/改装工种专用键的「值范围」与 `工坊v2-订单制设计草案.md` 的 tick 机制对应
- [ ] **域.键命名**与 `角色系统详细设计.md` §2 中 Zod Schema 的字段名完全对齐（如 `域` / `键` / `值` 三个子字段）
- [ ] 白名单确认后，商城解析器（`skillEffectWhitelist.ts`）能据此做白名单校验，未知 `域.键` 不入库

**输出**：确认版 `docs/技能mod白名单.md`，如有修改同步更新下游文档

### 0.2 消息格式规范对齐

**输入**：`docs/消息格式规范.md`

**检查项**：

- [ ] 玩法内部协议（`<Character>`、`<Skill>`、`<event>` 等）与 VN 主舞台协议的命名空间无冲突
- [ ] 玩法协议**不污染** VN 主舞台：所有 `<Character>`、`<event>` 等标签仅在玩法 UI 内部或聊天消息中作为 CMD 载体，不作为 `<content>` 等 VN 硬协议的一部分
- [ ] `callSecondApi` 的 task 类型列表中，为角色/工坊新增的 task 名称（`roleProfile`、`workshopOrder`、`dispatchStory` 等）无重复

### 0.3 类型定义预审

**输入**：`docs/角色系统详细设计.md` §2 TypeScript 类型定义

**检查项**：

- [ ] `角色Schema` 的 `catchall(z.any())` 与聊天变量实际存储格式兼容（yaml 解析层能处理任意额外字段）
- [ ] `技能效果Schema` 的三字段（`域` / `键` / `值`）与白名单校验逻辑的键名一致
- [ ] 角色状态枚举（`空闲/派遣中/工坊中/逃跑中/休息中/加班中/受伤`）与工坊 v2 草案中的状态机描述一致
- [ ] `DispatchActive` / `DispatchRun` / `OrderRun` 的字段名与 `废土行路模块详细设计.md` §2 和 `工坊v2-变量清单与清空机制.md` 完全一致，无命名漂移

## 3. 阶段一：角色系统·底层

> 目标：完成角色系统的**数据基础设施**——类型定义、扫描引擎、CMD 协议、ID 管理。不涉及 UI 和 AI 生成。

### 交付物清单

| # | 文件 | 内容 | 校验要点 |
|---|---|---|---|
| 1 | `src/galgame/types/role.ts` | 所有 Zod Schema + 类型别名 | Schema 能 parse 来自聊天变量的 yaml 对象 |
| 2 | `src/galgame/utils/roleScanner.ts` | 聊天扫描引擎（增量/全量 + 检查点） | 防抖 800ms、增量和全量路径均覆盖 |
| 3 | `src/galgame/utils/roleIdGenerator.ts` | 角色 ID / 技能 ID 自增管理 | 读写 `role_max_id` / `skill_max_id`，线程安全（单前端无并发问题） |
| 4 | `src/galgame/utils/skillEffectWhitelist.ts` | 白名单校验 + 随机数值分配 | 所有白名单键（派遣 A~E / 工坊 / 猜谜）均有对应随机生成函数 |
| 5 | `store.ts` 扩展 | 角色系统变量读写封装（`getRoles` / `updateRole` / `getSkills` 等） | 与 `角色系统详细设计.md` §1.1 顶层变量列表一致 |

### 阶段一内部校验检查清单

#### 扫描引擎

- [ ] 增量扫描：能从检查点恢复 `db_map` 和 `max_id`，不重复处理已扫描消息
- [ ] 全量扫描：能正确处理删楼/回滚/修改楼层后的状态重置
- [ ] 防抖：800ms 内的多次触发只执行一次扫描
- [ ] 事件监听：覆盖 `CHARACTER_MESSAGE_RENDERED`（增量）、`MESSAGE_DELETED/SWIPED/UPDATED`（全量）、`generation_started`（按检查点选择）、`CHAT_CHANGED`（全量+清除状态）
- [ ] 手动触发：提供 `performScan('full')` 入口供 UI 调用

#### CMD 协议

- [ ] `CMD:ADD`：能解析任意数量 `键:值` 对，支持自定义字段，支持 `属性:战力:3/技巧:2/...` 格式
- [ ] `CMD:MOD`：能修改任意字段，包括装备层和状态层
- [ ] `CMD:DEL`：同时从 `role_db_map` 和 `roles` 移除
- [ ] `CMD:EQUIP` / `CMD:UNEQUIP`：正确操作 `已装备技能` 数组
- [ ] `CMD:ADD_SKILL`：解析 `mod:域.键` 并调用白名单校验，通过后才入库
- [ ] `CMD:DEL_SKILL`：从 `skillsInventory` 和 `skill_db_map` 同步移除
- [ ] 所有正则表达式对中文/英文冒号（`:` / `：`）、竖线（`|` / `｜`）均兼容

#### 白名单校验

- [ ] 未知 `域.键` 拒绝入库，不展示，不触发错误
- [ ] 百分比/整数/布尔键的数值在白名单范围内，超出则截断或使用默认值
- [ ] 每个技能只能包含一个 `mod:`（单 mod 限制）

#### 变量读写

- [ ] 初始化时能从聊天变量正确恢复所有角色和技能数据
- [ ] `updateRole` 后数据能正确回写，无 proxy 层泄漏（需用 `klona()` 去除）
- [ ] ID 自增在并发场景下（连续快速添加多个角色）不重复

#### 弹幕 tick 引擎

- [ ] tick 按 `工坊v2-弹幕文本模板库.md` 的分类（纯展示/顺利推进/返工卡壳/灵感/摸鱼/加班/疲劳/事故逃班）正确抽取
- [ ] 纯展示类弹幕按角色属性（技巧/智慧/谨慎/社交/运气/战力）加权
- [ ] 进度秒增减公式（`进度秒 += 增减秒`，上限 `clamp(0, 订单时长秒)`）正确
- [ ] 加班模式下允许进度超出 100%
- [ ] 疲劳 `+1` 正确触发，到达阈值时强制下班
- [ ] 干涉权重衰减系数正确应用（长单 240~300 秒时系数 0.4）
- [ ] `工坊.通用正向tick权重` / `工坊.通用负向tick权重减免` / `工坊.通用疲劳增长减免` 等 mod 正确影响 tick 概率

#### 车间氛围（全局倍速）

- [ ] 车间倍速实时计算（当前所有在工坊工作的角色的 `社交` 属性）
- [ ] 社交每点 +5% 倍速，上限受 `工坊.车间氛围上限提升` 技能影响
- [ ] 多人同时工作时倍速正确叠加/平均

#### 订单结算

- [ ] 进度比例 = `进度秒 / 订单时长秒`（允许 > 1）
- [ ] 金币 = `floor(基础金币 × 进度比例 × 车间倍速 × 技能加成)`
- [ ] 订单内疲劳达到阈值 → 角色状态改为 `休息中`；未达阈值 → 疲劳不保留
- [ ] 逃班/事故 → 角色状态改为 `逃跑中` 或相应异常状态
- [ ] 订单结束后从 `进行中订单[]` 移除，弹幕在所有订单清空后自动清空

#### 变量持久化

- [ ] 所有订单字段（见 `工坊v2-变量清单与清空机制.md` §2/3）正确读写聊天变量
- [ ] 刷新页面后能从 `进行中订单[]` 恢复所有订单的运行态（通过 `开始时间戳` + `进度秒` + 当前时间推导）

## 7. 阶段五：收尾与联调

> 目标：确保所有模块之间的接口对齐，完成 end-to-end 流程校验。

### 7.1 跨模块接口校验

| 接口 | 校验项 |
|---|---|
| 角色系统 → 废土行路 | 派遣角色能从 `roles` 中正确获取，装备技能效果能被 `dispatchEngine` 读取 |
| 角色系统 → 工坊 v2 | 工坊中工作的角色能从 `roles` 中获取状态（`工坊中` / `加班中`），状态切换正确 |
| 废土行路 → 角色记录 | `settlement.ts` 调用 `appendRoleLog`，格式与 `角色记录写入格式设计.md` §3 一致 |
| 工坊 v2 → 角色记录 | `workshopSettlement.ts` 调用 `appendRoleLog`，格式与 `角色记录写入格式设计.md` §4 一致 |
| 商城 → 角色系统 | 技能购买后写入 `skillsInventory`，装备/卸下时 `已装备技能` 数组正确更新 |
| `callSecondApi` | 所有新增 task（`roleProfile`、`workshopOrder`、`dispatchStory`、`danmaku` 等）在 `store.ts` 中已注册 |

### 7.2 端到端场景校验

以下场景需要在真实环境中完整走一遍，验证数据流不断裂：

**场景 A：角色生成 → 装备技能 → 废土行路 → 结算回写**

1. 玩家在角色管理面板生成一个新角色
2. 玩家从商城购买一个派遣技能，装配到该角色
3. 玩家选择该角色进入废土行路
4. 派遣过程中角色属性和技能正确影响事件抽取和结算
5. 结算后金币入账，角色状态正确更新，记录中新增一条派遣日志

**场景 B：订单生成 → 角色指派 → 弹幕 tick → 结算回写**

1. 玩家刷新工坊订单，从第二 API 获取一批订单
2. 玩家指派一个工坊中的角色接单
3. 角色状态变为 `工坊中`，弹幕开始滚动
4. tick 正确增减进度秒，技能 mod 正确影响 tick 权重
5. 订单完成后金币入账，角色状态恢复，角色记录中新增一条工坊日志

**场景 C：角色状态冲突处理**

1. 角色处于 `派遣中` 时，工坊面板不能指派该角色
2. 角色处于 `工坊中` 时，废土行路入口不能选择该角色
3. 角色处于 `休息中` 时，需要手动或等待恢复后才能再次使用
4. 刷新页面后，状态恢复正确，所有进行中的订单/派遣状态完整

### 7.3 数据一致性校验

- [ ] 所有涉及 `角色.记录` 的写入操作都通过 `appendRoleLog()` 统一入口，不直接 push 数组
- [ ] `appendRoleLog()` 自动截断超过 100 条的旧记录
- [ ] 角色删除时，该角色不处于任何运行态（派遣中/工坊中/休息中）
- [ ] 技能删除/卸下时，正在使用该技能的角色的 `已装备技能` 数组同步清理
