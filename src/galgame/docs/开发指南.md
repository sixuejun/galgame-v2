## 1. 快速开始

### 1.1 安装

```bash
pnpm install
```

### 1.2 开发与同步

本项目运行在酒馆（SillyTavern）网页环境，通过酒馆助手实现热更新。

- 你只需要修改 `src/galgame/**` 下的代码/样式。
- 若酒馆助手的“实时监听”已开启，保存代码后会自动热重载。

### 1.3 代码入口（v1）

v1 的脚本入口是：`src/galgame/index.ts`。

它负责：
- 挂载单实例 UI（`host: 'iframe'` 且仅渲染在 0 楼）
- 监听酒馆事件（流式 token、生成结束、新楼层渲染、消息更新）
- 触发第二 API 辅助任务（弹幕/生图标签等）

## 2. v1 运行形态与核心约束

### 2.1 单实例渲染（必须）

v1 采用“只渲染一个实例”的架构：
- UI 被挂载为 `iframe`
- 仅显示在消息楼层 `message_id === 0`

这保证了：
- 历史楼层浏览可以在同一套 UI 内完成
- UI 状态不随楼层重复创建而丢失

### 2.2 Store 策略（外观保持单文件）

重构策略采用 **monolith facade**：
- 对外继续由 `src/galgame/store.ts` 提供统一的 `useVNStore()` 与方法集合
- 内部允许逐步抽离到 `utils/`、`composables/`、`components/`，但对外 API 尽量稳定

这条约束用于控制重构风险，避免大面积改动组件。

## 3. 消息协议与解析（强约束）

### 3.1 目标

v1 重构要求严格使用统一消息协议（见 [消息格式规范](./消息格式规范.md)）：

- **assistant 消息必须包含 `<content>...</content>`**
- `<content>` 内使用 `[[...]]` block 描述对话/旁白/选择/黑屏等
- `<dm>`、`<background>`、`<cg>` 等标签位于 `<content>` 外（解析器会分别提取）

### 3.2 解析原则

- VN 主舞台只显示 `<content>` 内的内容
- 未遵守协议的消息：视为“无 VN 内容”（UI 不展示）

## 4. 导航：历史楼层与跨楼层 block 规则

### 4.1 核心数据结构

v1 以 `dialogues[]` 维护楼层序列，每个楼层解析为 `blocks[]`：

- `dialogues[i]`：第 i 个楼层（按 messageId 排序）
- `dialogues[i].blocks[j]`：第 i 楼层的第 j 个 block

### 4.2 翻页与跨楼层

约定：
- 翻页单位是 block（不是字符）
- 当前楼层的 block 用完，自动切换到下一楼层的第一个 block
- 退回时同理：当前楼层越界则切到上一楼层最后一个 block

这部分规则是“连续阅读体验”的核心，不允许玩法模块破坏它。

## 5. 第二 API：任务、Prompt、解析与降级

### 5.1 权威来源：SystemPrompt 模板文档（B 方案）

v1 的第二 API Prompt **以 `src/galgame/docs/SystemPrompt模板.md` 为权威来源**。

要求：
- 代码层只引用 Prompt 的 key（例如 `danmaku`/`imageTag`/`shop`/`system` 等）
- Prompt 内容只能在本文档中修改
- 返回格式必须与解析器严格对齐（见本文档各节）

### 5.2 任务列表（建议）

- `danmaku`
- `imageTag`（背景/CG 统一）
- `danmakuAndImageGen`
- `shop`
- `riddle`
- `system`
- `boardGameEvent`

### 5.3 降级策略

当第二 API 未配置/超时/失败时：
- 对用户可见的玩法：提示“不可用原因”（例如需要配置第二 API）
- 对非关键功能（弹幕、生图标签）：静默跳过或提示一次即可

## 6. 主题系统：CSS 变量与覆盖优先级

v1 的主题系统基于 CSS 变量：

- 主题内置变量（ThemeDefinition.cssVars）
- 用户自定义 CSS 中的变量覆盖

约定：
1. `--theme-*` 为稳定公共语义变量
2. 组件内部不得直接依赖某个具体主题的私有变量

---

## 7. 玩法模块：插件化边界（在 v1 内实现）

v1 的玩法模块以 Overlay / ModuleView 形式存在。

重构目标：
- 把每个玩法模块视为“插件”，拥有明确输入输出：
  - 输入：读取 store 中的游戏状态、读取当前剧情上下文（必要时）
  - 输出：只通过 store 的 action 改变状态（金币、背包、日志、事件结果等）

玩法模块不得：
- 直接操纵 VN 导航（楼层/块索引）
- 绕开消息协议直接写入 UI

---

## 8. 重构分段建议（保持可运行）

建议按“协议 → 状态机 → 抽离依赖 → UI → 插件边界”顺序推进：

1. **协议落地**：消息格式规范 + 解析器行为固定
2. **导航状态机**：历史浏览 + 跨楼层 block 连续阅读
3. **第二 API Prompt 迁移**：让 Prompt 100% 由文档驱动
4. **主题系统收敛**：统一 `--theme-*` 语义与覆盖优先级
5. **玩法插件化边界**：把玩法模块的输入输出固定为 store action
